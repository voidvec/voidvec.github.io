简介

本文件面向 Fulla 的“会话管理”能力，围绕授权码交易、Bearer 访问/刷新令牌、社交绑定 Cookie、撤销级联、缓存/introspection、过期与截止策略及配置排障进行说明。Bearer 是受保护 API 的主认证机制；Redis 中可能存在授权交易与令牌缓存，不等于存在以 JSESSIONID 为凭据的服务端 Web 会话。短期 __Host-fulla-social-binding 只绑定社交 authorize/exchange 事务，不是认证会话。

项目结构

与会话管理直接相关的代码分布在以下层次：

  • 控制器层：SessionController 暴露登录、同意、登出等 HTTP 端点，并集成身份服务与会话管理器。
  • 身份层：SessionManager 负责登录策略评估与跨通道登出通知。
  • 存储层：Redis 仓库基类与各具体仓库（令牌、授权码、同意记录）负责持久化与 TTL 管理。
  • 插件层：OAuth2Plugin 统一装配服务与存储后端，并在关闭时释放资源。
  • 前端与安全测试：通过 E2E 用例验证 CSRF 防护与 Bearer 方案。

核心组件

  • SessionController：定义 /login、/oauth2/login、/oauth2/consent、/oauth2/logout、/api/register 等端点；支持注入 identity 服务与会话管理器，并提供回退路径兼容旧实现。
  • SessionManager：封装登录策略评估（邮箱验证、MFA）与跨通道登出通知调用。
  • Redis 存储基类与各仓库：提供 Redis 连接初始化、超时设置、原子脚本执行、TTL 管理；令牌与授权码采用 SETEX + JSON 序列化，利用 Redis 原生 TTL 自动清理。
  • OAuth2Plugin：集中管理服务与存储对象生命周期，在停止时释放引用，保证回调完成后再析构。

架构总览

下图展示授权码签发与 Bearer 使用的主路径：客户端向 /oauth2/login 提交凭证，控制器评估身份策略，成功后保存授权码/交易或返回授权码；客户端用授权码 + PKCE 换取 token pair。后续受保护 API 请求携带 Authorization: Bearer，不以 JSESSIONID 作为主认证凭据；登出/撤销按令牌与族处理。Redis 可保存交易、同意、绑定 state 与正/负缓存，Postgres master 是未发布安全读的权威来源。

详细组件分析

会话生命周期管理

  • 会话创建
    • 入口：/oauth2/login（POST）。控制器接收用户名、密码、client_id、redirect_uri、scope、state 等参数，并进行校验。
    • 策略评估：调用 SessionManager::evaluateLoginPolicy，依据邮箱验证与 MFA 策略决定 Proceed/RequireMfa/DenyEmailNotVerified。
    • 授权码/交易：按存储配置保存授权码或授权交易；Redis 模式使用 JSON 与 SETEX。未发布 require_pkce 默认要求所有 authorization_code 客户端提供 S256 challenge。
    • 认证凭据：授权码换取第一方 access/refresh token pair；受保护 API 使用 Bearer。社交流程额外使用 600 秒 HttpOnly 绑定 Cookie，但它不是认证会话。
  • 会话验证
    • 受保护端点通过过滤器要求认证；未认证返回 401。
    • validateAccessToken 检查记录存在、revoked 与 expires_at，不检查 not_before；Redis 正缓存读取/回填及 PostgreSQL introspection 另有 nbf 边界，不能把内省结果当作所有普通令牌校验的统一行为。
  • 会话更新
    • 刷新令牌通过 grant 轮换，不以“每次访问续期 JSESSIONID”为模型。
    • 缓存使用绝对 refill 截止；未发布 Redis refill 由服务器 TIME 检查 expires-at，不延长令牌寿命。
  • 会话销毁
    • 登出：/oauth2/logout 触发 SessionManager::logout 与跨通道通知，并由令牌撤销路径终结相关访问/刷新族。
    • 清理：Postgres 可执行过期清理；Redis 键依赖 TTL，但正缓存的 TTL 是收敛窗口，不表示撤销立即生效。

登出/撤销级联与口令重置撤销修复（v1.2.0）

增量补篇：2026-09 逐行审计 P0-2/P0-3 两项修复，总览见 [[versioning-and-release-guide-zh]] 与 [[security-hardening]]。

  • 登出/撤销级联修复（审计 P0-2）：revokeAccessToken 内部的级联此前把传入访问令牌的哈希匹配到错误的列（刷新令牌自身的哈希列），永远不命中——访问令牌撤销与登出之后，配对的刷新令牌仍可用至多 30 天。现在级联按 access_token 列连接，并额外杀死整个轮换族：登出时提交的（可能已过期的）访问令牌与已轮换出的刷新令牌同死。
  • 口令重置撤销双键化（审计 P0-3）：重置流程此前按内部用户 id 撤销令牌，而登录/MFA/社交的令牌行以 public subject 为键——响应声称已撤销全部会话，实际所有公键令牌仍然有效。现在撤销按双键进行（public_sub 或 内部 id，与账户删除的撤销形状对齐），同时消耗该用户全部未用的口令重置令牌。
  • 排障提示：升级到 v1.2.0 前签发、依赖旧级联漏洞存活的刷新令牌，在修复后的撤销/登出路径下会被正确终结；若仍观察到”登出后刷新令牌可用”，先确认实例已升级至 ≥ v1.2.0。

令牌存储与撤销（未发布当前主路径）

  • 权威存储：生产推荐 Postgres。getAccessToken、刷新 inspect/rotate 与 introspection 使用 dbClientMaster_，避免 lagging reader refill L2 安全缓存。
  • Redis 装饰器：RedisCachedTokenRepository 不是当前生产 refresh 主存储；它包装权威仓库，缓存 access 与 access-token introspection。cache_schema=2，两类值均序列化 orgId，旧 schema 拒绝。
  • 绝对截止与原子 refill：正缓存 EXAT 不晚于令牌 expires-at；Lua 用 Redis TIME 检查撤销 marker 与绝对截止，introspection 还要求对应 access 正键存在。已过期/撤销快照不得回填。
  • 5 秒 deadline：单次 lookup 的 steady-clock 截止覆盖 Redis lookup、master read 与 guardedFill；到点强制未命中/不活跃，无 stale positive fallback。Redis 命令错误可回读权威仓库，但不是返回旧缓存。
  • 单 token 撤销：权威 revoke 后写 negative marker（TTL 至少 60 秒），再 double-delete access/introspection 正缓存；marker/DEL best-effort，失败记录日志与指标。
  • 族撤销边界：checked family revoke 在存储事务内终结 RT/关联 AT，但不主动遍历清除全部正缓存；已有正缓存依赖 TTL 收敛，不能称全局即时撤销。
  • 刷新轮换（未发布）：hash → inspectRefreshToken → Memory 同锁 inspect+insert（失败回滚）或 Postgres family advisory lock 内重验 + 旧 RT CAS + 新 pair 事务 → confirmed commit 才返回 Rotated。明确重用才调用 revokeTokenFamilyChecked；StorageError/未知 COMMIT 返回 server_error，不误判 replay、不泄露 token。
  • 兼容性：Redis 独立 token 模式已弃用且拒绝 refresh grant；旧自定义 ITokenRepository 未实现 inspect/rotate/checked revoke 时，新默认接口 fail closed，不会回退旧撤销后签发流程。

会话安全特性与 introspection

  • 认证凭据
    • 受保护 API 以 Bearer access token 为主；前端不把 access/refresh token 放入 auth Cookie。
    • 社交绑定 Cookie __Host-fulla-social-binding 为 Secure/HttpOnly/SameSite=Lax/600 秒，仅用于一次性社交 state 事务，不能据此推断存在 JSESSIONID 会话。
  • 防重放
    • 授权码一次性消费；社交登录 state 以 SHA-256 digest 为 Redis key，Lua compare-delete 防并发重放，账号绑定 state 使用另一 store 的明文 key + GETDEL；refresh 轮换以锁内重验与 CAS 防重复轮换。
  • CSRF 防护
    • Bearer 不随 Cookie 自动发送，降低传统 Cookie CSRF 暴露，但不能称天然免疫所有 CSRF。社交流程仍要求允许 Origin、绑定 Cookie、服务端 state，并拒绝 Sec-Fetch-Site: cross-site、query 参数与重复键；CORS 白名单不是这些防护的替代品。
  • introspection（未发布）
    • 仅 active 响应带 metadata；无结果固定 {"active":false}，全部 no-store。
    • 普通校验：TokenService::validateAccessToken 检查记录存在、revoked 与 expires_at，不检查 not_before；RedisCachedTokenRepository::getAccessToken 的缓存读取与回填分支另行拒绝未到 not_before 的快照，是否经过缓存装饰层会影响该边界。
    • introspection：Postgres 仓库在 revoked/expiry 之外检查 not_before；非 memory 模式还要求 owner Active / Unmanaged，Suspended / Unavailable 拒绝。owner 指令牌客户端的所有者状态，不是用户活跃状态。owner 查询 60 秒缓存、5 秒 deadline，超时/DB error 不缓存，NoRow 才是 Unmanaged。
    • access-token introspection 可命中 schema=2 正缓存，refresh-token introspection 不缓存；org_id 是令牌事实，不是实时组织成员资格。

会话过期策略

  • 令牌绝对过期
    • access/refresh token 的 expires-at 由签发配置与签发时刻决定；缓存 EXAT/refill 截止不得晚于该值。Redis 到期删除只是存储机制，不构成滑动续期。
  • 授权交易 TTL
    • 授权码/交易使用 SETEX 与原子消费控制一次性有效期；社交 binding/state 为 600 秒。
  • 缓存绝对 refill 截止（未发布）
    • Redis TIME + Lua 在 refill 时拒绝到达绝对截止的旧快照；lookup 另有 5 秒 steady-clock deadline。正缓存不因访问而延长，族撤销后的已有正缓存只依赖 TTL 收敛。
  • owner 缓存（未发布）
    • owner 状态 memo 60 秒；错误/超时归类 Unavailable 且不写缓存。该缓存只影响 introspection 放行，不延长 token 本身寿命。
  • 配置影响
    • tokens.access_token_ttl、tokens.refresh_token_ttl 等驱动令牌寿命；测试断言 expires_in 与配置一致。

会话监控、调试与故障排查

  • 监控与日志
    • Redis 操作失败时记录错误日志（如 revoke/consent/token 操作异常）。
    • 插件停止时释放资源，便于定位生命周期问题。
  • CI 环境准备
    • 测试前等待 Redis 就绪（ping PONG），否则输出错误并中止，便于快速发现环境问题。
  • 常见问题定位
    • 若授权码无法消费：检查 Lua 脚本执行结果与 TTL 是否有效。
    • 若令牌撤销无效：检查 Redis 键是否存在及撤销逻辑是否命中。
    • 若登出不生效：确认跨通道登出通知器是否可用，以及会话标识是否正确清除。

  • 控制器依赖身份服务与会话管理器，并通过 OAuth2Plugin 获取服务实例；当未注入时使用回退路径。

性能考量

  • 使用 Redis 原生 TTL 减少后台清理任务开销。
  • 授权码消费使用 Lua 脚本原子操作，降低锁竞争与网络往返。
  • 令牌撤销采用条件更新，避免全表扫描与高延迟。
  • 合理设置 Redis 超时与连接池，避免阻塞请求。

故障排查指南

  • 登录失败
    • 检查邮箱验证与 MFA 策略；查看 SessionManager 决策分支。
  • 授权码无效
    • 检查 Redis 键是否存在、是否已被消费（Lua 脚本返回值）；确认 redirect_uri 匹配。
  • 令牌撤销不立即全局生效
    • 区分单 token negative marker 与 family revoke。已有正缓存可存活至 TTL；检查 cacheUntil、schema=2 与 marker/DEL 失败指标，不能把最终一致误报为“撤销完全无效”。
  • 刷新返回 server_error
    • 检查 inspect/rotate 的 StorageError、Postgres advisory lock、pair 插入或 COMMIT；未知 COMMIT 不记录 reuse、不返回新 token。
  • introspection active=false
    • 除 token revoked/expiry/nbf 外，检查 owner Suspended/Unavailable、5 秒超时和 60 秒缓存；错误/超时不缓存。
  • 登出不生效
    • 检查跨通道登出通知器是否可用；确认会话标识是否清除。
  • 环境就绪
    • 确认 Redis 服务可达（CI 中 ping PONG）；检查连接超时与错误日志。

结论

Fulla 的会话相关能力以授权交易与 Bearer 令牌为核心：控制器评估登录策略，Postgres master 提供权威令牌状态，Redis 保存交易/同意/社交绑定 state，并作为有绝对截止的 token cache 装饰层。未发布刷新轮换通过锁内重验、CAS、pair 事务与 checked revoke 降低竞争和误判；缓存有 5 秒截止且无 stale fallback。必须同时承认两处边界：族撤销依赖正缓存 TTL 收敛，不是全局即时撤销；Bearer + CORS 也不是所有 CSRF 的完整答案，社交 Cookie 事务仍有独立 Origin/state 防护。

  • 关键端点
    • POST /oauth2/login：登录并生成授权码或重定向。
    • POST /oauth2/logout：登出并触发跨通道注销通知。
    • GET /oauth2/authorize：授权端点；授权码客户端默认要求 S256（未发布 require_pkce）。

    • storage_type：选择存储后端。
    • tokens.*_ttl：令牌 TTL 配置。
