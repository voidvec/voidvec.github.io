项目/Fulla/部署运维
Fulla数据与运维进阶

1. 环境变量注入

应用支持用环境变量覆盖关键配置项。这在 Docker/Kubernetes 环境下尤为重要——
敏感信息不应硬编码在 config.json 中。

支持的环境变量

变量名 说明 覆盖的配置路径 示例
FULLA_DB_HOST 数据库主机名 db_clients[0].host postgres
FULLA_DB_NAME 数据库名 db_clients[0].dbname fulla_db
FULLA_DB_PASSWORD 数据库密码 db_clients[0].passwd secret
FULLA_REDIS_HOST Redis 主机名 redis_clients[0].host redis
FULLA_REDIS_PASSWORD Redis 密码 redis_clients[0].passwd secret
FULLA_PORTAL_CLIENT_SECRET 门户客户端密钥（旧名别名：FULLA_VUE_CLIENT_SECRET） plugins[OAuth2Plugin].config.clients.fulla-portal.secret ...

生产部署的完整环境变量清单（30+ 项）见生产部署的变量表；本表只列注入机制的六个核心项。

工作机制

  1. 加载钩子：启动时 main.cc 的 loadConfiguration() 先调用 common::config::ConfigManager::load()，再调用 ConfigManager::validate()。
  2. 解析：把基础 config.json 读入 Json::Value 对象。
  3. 注入：检查上述环境变量是否存在；存在则就地更新 Json::Value 中对应节点。
  4. 加载：Drogon 通过 drogon::app().loadConfigJson(config) 直接加载修改后的配置对象，磁盘上不产生临时文件。

验证

专用测试 EnvInjectionVerify（EnvConfigTest.cc）保证该逻辑正确。

.env 文件与进程环境

loadDotEnv() 把 .env 文件（相对工作目录按 .env、../.env、../../.env
搜索）解析到内存中；它从不把这些值导出到进程环境。读取这份结果的有两个入口，
生产代码中的每一次读取都必须经过其中之一（arch-guard 规则 R5）：

  • **能读到 .env**（ConfigManager::getEnv）：.env 优先于进程环境。上面的配置
    覆盖以及 FULLA_ENV 用的是它。
  • 只读进程环境（ConfigManager::getProcessEnv）：不查 .env 文件。对于承载
    凭据或决定启动行为、必须来自真实环境变量（由容器 / 编排器注入）的键，这是有意
    为之：FULLA_SIGNING_KEY、FULLA_JWT_KEY_PATH、FULLA_AUTO_MIGRATE、
    FULLA_BOOTSTRAP_ADMIN_PASSWORD、FULLA_BOOTSTRAP_ADMIN_EMAIL、FULLA_SMTP_*
    一族以及 DETAILED_VALIDATION_ERRORS。

第二组里的键如果写在了 .env 里，会被忽略，并且启动时会报告：

此前它是被静默忽略的。生产环境缺少签名密钥时的报错，对 FULLA_SIGNING_KEY /
FULLA_JWT_KEY_PATH 也说的是同一件事。

FULLA_ENV 在所有地方的读取方式现在是一致的。此前它有两处认 .env、两处不认，
于是只写在 .env 里的 production 会跳过签名密钥与客户端注册表检查。当 .env
与进程环境对它的取值不一致时，所有读取方都以 .env 的值为准，并且启动时会报告
这一分歧——请把 FULLA_ENV 只放在一个地方。

2. Docker 部署

仓库内置 docker-compose.yml 编排全栈（详解见 Docker 部署）。

服务栈

  • fulla-frontend：Vue SPA + Nginx（构建自 deploy/docker/Dockerfile 的 frontend-runtime）。
  • fulla-admin：管理后台前端（构建自 frontends/admin/Dockerfile）。
  • fulla-backend：Drogon 后端（构建自 deploy/docker/Dockerfile 的 backend-runtime）。
  • fulla-postgres：PostgreSQL 17（后端启动时经 FULLA_AUTO_MIGRATE=true 应用 apps/server/migrations/ 下的 schema）。
  • fulla-redis：带密码保护的 Redis 7。
  • fulla-prometheus：指标采集。

快速开始

Docker 下的配置处理

docker-compose.yml 将 apps/server/config/config.json 只读挂载进容器；
environment 段注入环境变量（见 §1），运行时经 ConfigManager::load() +
环境注入覆盖文件默认值。

3. 存储后端选择

OAuth2 插件的 config.storage_type 决定持久化后端：

storage_type 状态 说明
postgres 支持（唯一生产后端） 完整令牌持久化、refresh token 轮换与重用检测。
redis 已弃用 历史上从未持久化 refresh token（saveRefreshToken/getRefreshToken 为空操作），轮换与重用检测静默失效。该模式仍可启动（兼容考虑，启动时打 ERROR 日志），但 refresh_token 授权会以 unsupported_grant_type 被拒绝。新部署不要使用。
memory 仅测试 面向单元/集成测试，不用于生产。

目标架构：Postgres 作为存储层，前置一个在线 Redis L2 缓存（键空间
fulla:cache:*，经 config.json 的 cache 块配置 enabled /
ttl_seconds / invalidation_double_delete_delay_ms；失效采用延迟双删，
见 DelayedDoubleDelete）。不存在独立 Redis 存储模式。

4. Issuer 配置

config.metadata.issuer（custom config）是服务器 issuer URL 的唯一事实源。
OAuth2Plugin 启动时读取一次，一致地用于：

  • 签发 access token 时打上的 iss 声明（authorization_code / refresh_token / client_credentials / device_code 授权）；
  • 内省响应的 iss（存储行未携带时以配置值回填）；
  • 发现文档（/.well-known/openid-configuration、/.well-known/oauth-authorization-server）。

约束：

  • 末尾斜杠会被自动规范化掉，不要依赖它。
  • 未设置时默认 http://localhost:5555，此时打 LOG_WARN。
  • 生产部署必须配置 https:// issuer；非回环主机上使用明文 http issuer 会有启动告警。
  • 内省 iss 与发现文档 issuer 保证逐字节一致（OIDC Discovery §3 要求）。

4a. 管理后台 Origin 与设备验证 URI（#146）

config.admin_console.url（custom config）是管理后台 SPA 的 ORIGIN（scheme + host
[+ port]，不含 path）——生产环境如 https://admin.example.com，默认
http://localhost:5174（开发用 vite 服务器）。目前它只有一个消费方：RFC 8628
设备授权响应的 verification_uri/verification_uri_complete，二者默认为
{admin_console.url}/admin/devices——即真正的设备批准页面。#146 之前的默认值
指向 /oauth2/device，该路径背后并没有页面。

  • 显式覆盖：config.device_authorization.verification_uri（完整 URL）优先于
    推导出的默认值；verification_uri_complete 始终由推导得出
    （verification_uri + ?user_code=<code>）。
  • admin_console.url 的末尾斜杠会被自动规范化掉。

4b. 首次登录强制改密（#145）

以 users.must_change_password = true 创建的账号——引导创建的 admin（随机密码与
FULLA_BOOTSTRAP_ADMIN_PASSWORD 两种变体皆是）以及经管理 API 以
must_change_password: true 创建/更新的用户——必须先修改密码，之后才会签发
任何授权码：

  • /oauth2/login 返回 200 {"password_change_required": true, ...}，而不签发
    code；
  • /oauth2/authorize 重定向到前端登录页（由其渲染改密表单）；prompt=none
    返回 error=login_required；
  • POST /oauth2/consent 返回 403 AUTH_PASSWORD_CHANGE_REQUIRED。

改密路径为 POST /oauth2/password/change（会话认证，要求 old_password，强制
auth.min_password_length，撤销全部令牌，清除该标志）。PUT /api/me/password
同样会清除该标志。管理员对存量账号设置的该标志在该用户下次登录时生效。

4c. 授权端点的登录 / 授权确认跳转目标（WeKnora 修复 #3/#4）

当 /oauth2/authorize 需要用户参与时（未登录、被强制重新认证，或需要授权确认），
它会重定向到登录页 / 授权确认页。目标按以下优先级解析：

  1. config.oauth2.login_url / config.oauth2.consent_url——显式的绝对 URL
    （优先级最高；登录页 / 授权确认页部署在独立 origin 上时使用）。两者都可以
    用环境变量 FULLA_OAUTH2_LOGIN_URL 与 FULLA_OAUTH2_CONSENT_URL 设置。
  2. config.frontend.url + /login | /consent——默认值：用户 SPA 的路由，
    与邮件链接、注册链接使用的是同一个前端 origin。
  3. 旧版的后端相对路径 /login | /consent——仅当 frontend.url 缺失时使用
    （仅供开发环境兜底）。

历史上默认值是第 3 项；在只部署后端的环境里，这意味着一个没有样式的旧版登录页
（其内联样式会被后端 CSP 拦截），以及 /consent 的硬 404（后端没有这个 GET 路由
——授权确认页是前端 SPA 的一个路由）。因此，任何对外提供 RP 服务的部署，都必须
让 frontend.url（或显式的 oauth2.*_url 覆盖）指向 SPA 的 origin。在标准的
docker-compose 栈中，两者经由 FULLA_FRONTEND_URL 开箱即是正确的。

如果显式配置的 URL 本身已带有 query string，授权参数会以 & 而非 ? 追加
（保证重定向 URL 始终合法）。这些键的值若不是字符串，会被忽略（沿优先级列表
继续回退），而不会导致启动崩溃。

标准部署只设 FULLA_FRONTEND_URL 就够了：两个跳转目标都会跟随它。仅当登录页
或授权确认页部署在别处时，才设置 FULLA_OAUTH2_LOGIN_URL 与
FULLA_OAUTH2_CONSENT_URL（或直接修改配置文件里的这两个键）。环境变量覆盖
不会创建新键，所以每份随附配置都带有这两个键——值为空串，表示”未设置”。变量
已设置、但所加载的配置文件里没有对应键时，启动会报告，而不是静默忽略（见
deployment.md 的”后端配置”）。

相关说明：SPA 的授权确认页提交 POST /oauth2/consent 时带 json=true，并根据
返回 JSON 的 location 字段让浏览器自行导航——原生表单 POST + 302 会被 Chrome 的
form-action 强制拦截（它同样会检查表单提交之后的重定向）。对非 JSON 调用方，
302 契约仍是默认行为。

5. 客户端令牌端点认证方式（F-017）

每个客户端通过 oauth2_clients.token_endpoint_auth_method 列声明其在
/oauth2/token、/oauth2/introspect、/oauth2/revoke 的认证方式：

取值 语义
client_secret_basic 密钥必须走 Authorization: Basic 头；body 携带 client_secret 会被拒绝。
client_secret_post 密钥必须走 POST body；Basic 头会被拒绝。
none PUBLIC 客户端；携带任何 client_secret 都会被拒绝。
NULL / 空 旧版宽松回退：接受 Basic 头，也接受 body 密钥（Basic→body 回退）。

注册/管理端创建时若省略该字段，按以下默认值落库：

  • PUBLIC 客户端 → none（本就没有密钥）。
  • CONFIDENTIAL 客户端 → client_secret_basic。

种子客户端均显式声明：fulla-portal 与 fulla-admin-console → none；
backend-svc → client_secret_basic。已有 NULL 值的客户端保持升级前的
行为，升级不破坏存量部署。

WeKnora 修复（#6/#7）的增补：

  • 配置播种会读取该键。 启动播种器现在会从每个
    plugins.OAuth2Plugin.config.clients 条目读取 token_endpoint_auth_method
    （此前它完全忽略该键，对 CONFIDENTIAL 客户端总是写入 client_secret_basic，
    以致用 body 密钥认证的 RP 无法通过配置播种）。组合规则：PUBLIC 只接受
    none；CONFIDENTIAL 只接受 client_secret_basic / client_secret_post
    ——显式写出的非法组合会让该客户端播种失败，并输出一条启动 ERROR（该客户端
    不会被播种）。内存仓库适用同样的规则。
  • 管理 API 可以修改它。 PUT /api/admin/clients/{clientId} 接受
    token_endpoint_auth_method（取值域与组合规则相同，按该行的 client_type
    校验），管理控制台的应用详情页以下拉框的形式提供该字段。修改在令牌 / 内省 /
    撤销端点立即生效（F-017 读取客户端行；写入时会使客户端缓存失效）。

6. OIDC prompt / max_age / auth_time（F-022）

授权端点支持 OIDC Core §3.1.2.1 的 prompt 与 max_age 参数：

  • **prompt=none**：禁止任何 UI。无会话 → 302 error=login_required；
    需要同意 → error=consent_required。错误会带着回显的 state 重定向回
    已验证的 redirect_uri。none 与其他值组合（如 none login）自相矛盾，
    直接返回 400。
  • **prompt=login**：即使已有会话也强制重新认证。
  • **prompt=consent**：即使既有同意已覆盖所请求的 scope，也强制显示同意页。
  • **max_age=<秒>**：若会话的 auth_time（登录 / MFA 验证时设置）早于
    max_age，强制重新认证。

auth_time 与 amr 随授权码持久化，并在换票时打进 id_token：auth_time
（大于 0 时）、amr（设置时为 JSON 数组）、acr（1 = 仅密码，2 = MFA）。
发现文档宣告 prompt_values_supported、acr_values_supported 与相关 claims。

7. RP-Initiated Logout（F-027）与会话失效（F-028）

/oauth2/end_session（GET + POST）终结服务端会话。要在登出后重定向，
客户端须提供 post_logout_redirect_uri，且它必须是该客户端已注册的
redirect URI 之一；客户端由 id_token_hint 的 aud 声明识别。hint 的
签名会被验证（RS256 + kid + iss/exp/sub 策略，issue #78），验证失败以
400 AUTH_INVALID_ID_TOKEN_HINT 拒绝。没有合法 hint + 已注册 URI 时请求
被 400 拒绝；成功时带 state 回显 302 重定向，未提供重定向 URI 时返回 200。

POST /oauth2/logout（既有的 API 登出）额外调用 session()->clear()
（F-028），因此服务端会话随 access token 撤销一并终结。

8. 认证失败限流（F-018）

token / introspect / revoke / device-code 轮询四个端点共享一个进程内
滑动窗口限流器，按 (client_ip, client_id) 分桶。滚动窗口
（默认 60s）内失败计数达 max_failures（默认 30）后，后续请求返回
HTTP 429，带 Retry-After 头与 OAuth2 风格的
{error, error_description} 响应体。只计失败；一次成功即清零，因此
正常负载（以及大量连续成功请求的集成测试套件）不会被限流。

经 custom_config.auth.rate_limit 配置（所有 config*.json 都显式携带默认值）：

两个键均可省略；rate_limit 对象缺失时使用内置默认（30 / 60）。限流器是
函数局部单例（libs/common/include/fulla/common/utils/RateLimiter.h 的
RateLimiter::instance()），四个受保护端点在同一进程内共享一份计数表。
这是最小化的暴力破解/令牌探测防护；多实例部署需要共享存储（Redis），
为后续工作。

9. JWKS 密钥轮换（#110 —— keystore 目录）

plugins.OAuth2Plugin.config.oidc.signing_keystore_dir 指向一个 keystore
目录，即密钥轮换机制：

语义：

  • 签名始终使用 active_kid 指名的密钥；JWT 头携带该 kid。
  • 验签按令牌头部的 kid 在全部已加载密钥中路由，JWKS 端点
    （/.well-known/jwks.json）发布全部已加载公钥——只要旧密钥还在目录里，
    存量令牌就能继续解析。
  • GET /api/admin/oidc/keys 上报实时状态：每个 kid、哪个 active、哪些仅
    published。
  • keystore 优先于 FULLA_SIGNING_KEY / FULLA_JWT_KEY_PATH /
    signing_key_path；配置了但目录损坏是硬启动失败（绝不静默回退到其它
    密钥来源）。

轮换流程（JwkManager 设计为 init-once/只读，每步都要重启——一个周期三次
重启）：

  1. 发布：把新的 <kid>.pem 放入目录，重启。两把密钥都进入 JWKS；旧密钥
    继续签名。至少等待 JWKS Cache-Control max-age（1 小时）再进第 2 步——
    严格缓存的 RP 否则还解析不到新 kid。
  2. 切换：把 active_kid 改为新 kid，重启。新令牌携带新 kid；旧令牌仍可
    验签（旧密钥仍发布）。
  3. 退役：等最大令牌生命周期流逝后（按令牌 TTL 估算，不看第 2 步时钟），
    删除旧 <kid>.pem 并重启。旧密钥令牌从此验签失败（未知 kid）。

跳过第 3 步会让旧密钥永久发布（无害，但扩大泄露面）；提前执行则使旧密钥的
存量令牌失效。

密钥生成用标准工具即可，例如
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out 2026-12.pem。
像保护任何私钥材料一样保护该目录（文件权限 / secret 挂载）。

10. 旧版密码哈希迁移窗口（#103）

fulla 只通过 PBKDF2-SHA256（$pbkdf2-sha256$310000$<salt>$<hash>）校验密码。
1.0 之前的无盐 SHA256 格式已退役，且在所有路径上默认拒绝：

  • 所有发行配置中 auth.allow_legacy_hash 均为 false，且缺失该键同样视为
    false（装配层默认值）。为 false 时，针对旧格式哈希的登录尝试会在任何
    密码校验之前被拒绝——即使密码正确也一样。
  • 该拒绝是策略拒绝，而非密码错误：它不推进账号锁定计数器（仅凭一个用户名
    不应让攻击者锁死旧格式用户，之后重开窗口也不应被 locked_until 阻挡）。
  • 每次拒绝都会记录 AUTH_LEGACY_HASH_REJECTED（WARN）并附内部用户 id——这是
    面向运维、指出谁仍需迁移的信号。客户端始终收到通用的
    AUTH_INVALID_CREDENTIALS；从外部无法区分”旧格式被拒”与”密码错误”。

哪些部署受影响？ 仅限 v1.0.1 之前播种、且仍持有旧格式行的数据库。盘点 SQL：

无需开窗口的迁移路径：

  • 邮件密码重置——重置流程总是写入 PBKDF2，因此旧格式用户完成重置即透明迁移。
  • 管理员触发的重置——效果相同。

修改密码不会迁移旧格式用户：它通过同一条已退役的分支校验旧密码，因而必然
失败；请改用重置。

重开窗口（临时，仅限登录）： 设置 auth.allow_legacy_hash: true 并重启。
旧格式用户随后即可登录，并在首次成功登录时被透明地重新哈希为 PBKDF2（仅限
identity 登录路径）。由于策略拒绝从不推进锁定计数器，重开前无需解锁。盘点查询
返回 0 后即可再次关闭窗口；该窗口（以及 identity 侧的重新哈希代码）计划在
v1.1 移除。

11. WebAuthn / 通行密钥（#142）

通行密钥的注册与认证执行真实的密码学校验（W3C WebAuthn Level 2 §7.1/§6.1）：
仅支持 ES256，仅接受 fmt="none" 的 attestation，断言签名以注册时存储的 COSE
公钥校验。配置：

  • rp_id —— Relying Party id（凭据所绑定的可注册域名；本地开发用 localhost）。
  • rp_origins —— 可接受的 clientDataJSON origin 的严格允许列表。
    finish 端点接受任何请求之前必须先配置：列表为空（或缺少该键）时，注册/认证
    的 finish 一律 fail-closed。生产环境必须列出门户的确切 origin，例如
    ["https://auth.example.com"]。
  • challenge 有效期 300 秒（代码强制）。注册 challenge 绑定到 Bearer subject
    （注册端点位于令牌过滤器之后；SPA 不发送会话 cookie）；认证 challenge 绑定到
    调用方的会话——登录流程需要携带 cookie（credentials: 'include'）。
  • 两个 begin 响应中的 userVerification 均为 required，并在认证时强制校验
    （UV=1）——不具备用户验证能力的认证器无法在此注册凭据（否则它们永远无法
    通过认证）。签名计数回退按认证器克隆处理：拒绝该断言并记录
    webauthn_clone_detected 审计动作。
  • V028 清空了所有既有凭据行：此前存储的每一行都是客户端自行声明、从未通过
    attestation 校验的材料（且 authenticateFinish 过去会把一个裸凭据 id 当作持有
    证明接受）。用户升级后需重新注册通行密钥。
  • 单实例部署：绑定 subject 的注册 challenge 存储在进程内（与 consent_csrf nonce
    属同一类局限）。多实例部署需要共享的 challenge 存储（后续工作）。

12. 邮件模板（P1-2，#278）

三封生产邮件（邮箱验证、密码重置、组织邀请）改为从数据库模板渲染
（V040 email_templates：3 个 key × en/zh-CN 种子，每行含主题 +
HTML + 纯文本）。发送通道仍由环境变量驱动（FULLA_SMTP_* 选择 Console
或 SMTP）；模板在其上叠加本地化、可编辑与 multipart/alternative HTML
投递。

管理 API（admin 角色 + roles:read/roles:write scope）：
GET /api/admin/email-templates、GET|PUT /api/admin/email-templates/{key}/{locale}、
POST /api/admin/email-templates/{key}/{locale}/test-send。仅 Postgres——
memory 部署返回 404（无模板存储；实际发送时引擎回退到编译期内建模板）。

模板变量使用 {{name}} 占位符；引擎对每个替换值做 HTML 转义（组织名是
无过滤自由文本）。保存时内容策略拒绝 <script>/<iframe>/<form>/<object>/ <embed>/<base> 标签、javascript:/data:/vbscript: URL，以及任何
不在允许列表内的外链 http(s) href（见下方 allowed_link_domains），
返回 EMAIL_TEMPLATE_CONTENT_REJECTED（400）。

配置（custom_config）：

  • allowed_link_domains —— 保存模板中字面 http(s) href 允许的主机
    （精确或子域匹配；条目接受裸主机或 https://host/ 写法）。为空或缺省
    = 不允许任何外链；变量链接（{{verify_link}}、{{reset_link}}）由引擎
    供给，不受此列表影响。
  • test_recipients —— 管理端 test-send 额外授权的收件地址（各管理员
    本人账号邮箱始终允许）。
  • test_send_quota_per_day —— 每管理员滚动 24 小时 test-send 配额
    （默认 10；按最近 24 小时的 email_test_sent 审计行计数——刻意不是
    自然日）。
  • allow_org_logo —— 邀请模板中组织品牌变量的占位开关；邮件中的远程
    组织 logo 是收件人打点隐私面，默认保持关闭    。种子模板不引用组织
    logo 变量。

链接信任锚（D8 红线）：验证与重置链接的域名只来自全局 frontend.url
配置——组织可控的输入永远不会被拼进安全链接；且无论配置如何，验证/重置
邮件不携带组织品牌。

13. 审计日志导出与保留（P1-6，#283）

GET /api/admin/logs/export（admin 角色 + audit:read scope）以 CSV 附件
形式导出审计流水。过滤器与列表端点相同（action/outcome/actor_id），
另加强制时间窗（from/to，unix epoch 秒）——除非调用方以 all=true
显式选择全表；行数硬上限防止无界导出。单元格做了公式注入加固：以
= + - @ 或制表符/CR 开头的单元格前置撇号（OWASP）——user_agent、ip
与 details 完全用户可控，导出是注入出口。每次导出都会写审计
（audit_exported）。

配置（custom_config）：

  • retention_months —— 审计保留窗口（默认 0 = 永久保留）。清理周期
    （与推进分区前瞻的同一周期）会 DROP 整个月都在窗口之前的
    audit_logs_pYYYY_MM 月分区。只有精确匹配该命名模式的分区才会成为
    候选；DEFAULT 分区永远不会被 DROP。被 DROP 历史的恢复方式 = 重新导入
    导出的 CSV。
  • export_max_rows —— 导出行数上限（默认 50 万）。请求级 limit 参数只
    允许调低；超限导出返回 400 AUDIT_EXPORT_TOO_LARGE 并提示收窄窗口。

14. 品牌化消费链 + PKCE plain 移除（P1-1，#279）

PKCE plain 现被无条件拒绝。 v1.5.0 作为单版本过渡发布的
auth.allow_pkce_plain 逃生阀已移除（过渡窗口已关闭）。配置键已删除：
authorize 处 code_challenge_method=plain 无论配置如何都返回
invalid_request；discovery 只公告 S256。仍依赖 plain 的部署必须在升级
v1.6.0 前把客户端迁移到 S256。

品牌化消费。 组织与客户端品牌字段现在到达用户侧界面：

  • GET /oauth2/authorize-context（additive）：客户端 logo_uri，以及
    应用归属组织时的 {org_name, logo_uri?, primary_color?} 块。
  • GET /oauth2/consent/context（additive）：客户端展示块、本地化的
    scope_descriptions（见下）、org 横幅上的品牌字段。品牌仅作展示、
    不受信——始终与所有者归因标签成对渲染。
  • 同意屏的 logo 只以 <img src> 渲染（SVG 在 img 上下文不执行脚本；
    禁止以锚点包裹）。nginx 层（用户 + 管理 SPA）现在下发
    Content-Security-Policy（img-src 'self' data: https:）——此前两个
    SPA 完全没有 CSP。

写路径与校验（V041 增加 oauth2_clients.logo_uri 与
oauth2_scopes.description_zh）：管理端客户端创建/编辑、门户我的应用
创建/编辑接受 logo_uri；组织自助创建校验两个品牌字段。规则（刻意
不是 redirect 注册规则）：

  • logo_uri：仅 https，回环主机豁免（开发用），禁 userinfo/fragment，
    ≤512 字符——不继承 auth.allow_http_redirect_uri。
  • primary_color：^#[0-9a-fA-F]{3,6}$（原先无约束；列宽 VARCHAR(7)）。
  • description_zh（作用域管理 CRUD，≤512 字符）：中文同意屏文案。
    consent context 按页面语言服务端下发；前端字典仅作缺失兜底。描述
    变更带前后 diff 写审计（scope_updated）。

15. RBAC 权限 enforcement（P1-8，#285）

委托管理已上线：三道门 RBAC 模型（ADR-0014 修订 1）——scope 分层（链①）、
IdentityService scope 检查（链②）、AuthorizationFilter 角色/权限门（门③）
——现在从 role_permissions 目录解析权限（V043 种子；V005 旧名原地标记
退役）。

  • rbac_rules 对象形式（additive）：条目可以写
    {"permissions": ["users:read"]} 替代角色数组——调用者的
    角色→权限并集须覆盖每个列出的名字。具体规则先于
    /api/admin/.* -> ["admin"] 兜底匹配（加载时强制最具体优先）。
    发行配置演示了 helpdesk 形态：/api/admin/users.* 要求
    users:read。
  • 分类与判定解耦：哪些 scope 属 admin 级仍来自
    oauth2_scopes.requires_admin_role（本版继续读取的弃用列）；用户能否
    通过改为按权限判定（或字面 admin 超角色）。给角色授 scope 永不改变
    分类。
  • 登录路径同样分层：两步门户登录铸造的 code 只包含三层引擎判定
    通过的 scope（此前未过滤——委托控制台会拿到其用户无权限的 admin 级
    scope）。
  • 角色权限管理：GET/PUT /api/admin/roles/{id}/permissions
    （全量替换；名字必须全部存在；审计 role_permissions_updated；提交时
    单实例缓存失效——多实例漂移是已知局限，P3 共享存储解决）。
  • memory 模式：编译期默认映射（admin → 全十项，user → 无）镜像
    V043 种子。
