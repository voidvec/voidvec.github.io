简介

本文件面向Fulla的OAuth2/OIDC协议安全实现，聚焦以下主题：

  • PKCE（RFC 7636）的实现原理与安全优势
  • JWT令牌的签名机制与算法（RS256等）
  • 客户端认证方式（客户端密钥、私钥JWT、公钥认证）
  • 授权码流程的安全增强（state参数、重定向URI白名单、防重放）
  • 刷新令牌的安全管理（轮换、家族化、撤销）
  • OIDC Discovery与JWKS端点的安全实现
  • 安全配置指南与合规性检查清单

项目结构

本项目将OAuth2/OIDC能力以插件与库的形式组织：

  • libs/oauth2：协议核心（PKCE、令牌服务、仓库接口）
  • libs/drogon：控制器与OpenAPI注册（授权、同意、发现、JWKS）
  • libs/common：通用端口与模型（加密抽象、PKCE值对象）
  • libs/storage-*：存储实现（Postgres、Redis、内存）
  • apps/server：服务端应用（迁移、种子数据、OpenAPI文档）
  • docs：后端集成指南、运维安全清单等

详细组件分析

PKCE（RFC 7636）实现与安全优势

  • 实现要点
    • 仅支持 S256 挑战方法（v1.5.0 起，RFC 9700 §2.1.1 方向）：code_challenge_method=plain 被授权端点拒绝，省略方法不再按 RFC 7636 §4.3 默认 plain，challenge 必须显式声明 S256。
    • 默认强制范围（未发布）：custom_config.auth.require_pkce=true 为代码与配置默认值，适用于所有 authorization_code 客户端；旧键 require_pkce_for_public 已硬切割、不再读取。显式关闭是部署选择，不应把“仅 public 客户端”当作现行语义。
    • S256 使用SHA-256后Base64url编码。
    • 提供code_verifier格式校验（长度43-128，字符集符合RFC 7636 §4.2；v1.2.0 审计 P0-4 起在全部四条签发路径强制执行）。
    • 通过ICryptoProvider抽象进行哈希与编码，便于替换底层实现。
  • 安全优势
    • 防止授权码在公共客户端被中间人截获后滥用。
    • S256-only 使明文 code_verifier 比对从协议面上消失。
  • 关键路径
    • 计算challenge：computeCodeChallenge
    • 验证verifier：verifyCodeVerifier
    • 值对象封装：PkceChallenge

JWT令牌的签名机制（RS256）

  • 实现要点
    • 使用RSA私钥对JWT进行RS256签名（EVP_sha256 + RSA）。
    • Header包含alg=RS256、typ=JWT、kid标识密钥。
    • JWKS端点输出对应公钥（n,e），供客户端验证签名。
  • 密钥加载
    • 优先从环境变量FULLA_SIGNING_KEY或FULLA_JWT_KEY_PATH加载PEM私钥。
    • 未配置时生成临时密钥（仅开发环境）。
  • 安全建议
    • 生产环境必须配置持久化私钥并定期轮换。
    • 客户端应缓存JWKS但设置合理刷新策略，并校验kid与alg。

授权码流程的安全增强

  • state参数
    • OAuth2 RP 应在授权请求中生成不可预测 state，并在回调时严格比对；Fulla 将其回传到已注册 redirect_uri。
    • 社交登录是另一条服务端状态化链路（未发布）：GET /api/auth/providers 的 legacy authorize_url 固定为空且 deprecated；先两阶段 POST /api/auth/providers/{provider}/authorize 获取绑定 Cookie 与 600 秒 state，exchange 再以 JSON/form 提交 code+state，并带 Origin/Cookie。Redis 仅存 SHA-256 digest，NX+EX 保留、Lua compare-delete 消费，拒绝 query、重复键、跨站与重放；Redis 故障 fail closed。详见 [[authentication-security-social-login-security]]。
  • 重定向URI白名单
    • 消费授权码时必须校验redirect_uri与授权请求一致，防止重定向劫持。
    • 错误码边界：代码签发路径发现 redirect_uri 未注册使用 VALIDATION_CLIENT_REDIRECT_URI_NOT_REGISTERED（3027）；VALIDATION_REDIRECT_URI_NOT_REGISTERED（3013）是 end_session 专用，不能复用为代码签发错误。
  • 防重放攻击
    • 授权码一次性使用；结合PKCE确保即使授权码泄露也无法被第三方复用。
  • 实现位置
    • 会话控制器在同意/授权完成后生成授权码并重定向。
    • 令牌服务在消费授权码时校验redirect_uri与PKCE。

刷新令牌的安全管理（轮换、家族化、撤销）

未发布加固：以下替换旧的 atomicRevokeRefreshToken + 回退 getRefreshToken 流程。历史版本曾使用该路径；当前基线的安全正确性以 inspect → 锁内重验 → CAS/insert pair → confirmed commit 为准。

  • 家族化管理
    • 同一授权码派生的所有刷新令牌共享 family_id，便于批量撤销。
    • 刷新先计算哈希，调用 inspectRefreshToken(hashedRt, clientId)。实现必须区分存储失败与不存在，并在报告重用前校验客户端绑定；ClientMismatch、Expired 不签发。
  • 轮换与重用检测
    • TokenService 再校验 client/expiry，保持族、scope、org 与主体绑定，生成新的 access/refresh token pair，然后调用 rotateRefreshToken(expectedOld, newAccess, newRefresh, ...)。
    • Memory：同一 recursive mutex 内完成 inspect 与 insert；插入 access/refresh 任一步失败会回滚已插入记录，旧令牌保持可用，返回 StorageError。
    • Postgres：master 初查后取得 family advisory lock，在锁内再次从 master inspect，校验 family/user/scope/org/client/pair 关系；对旧 RT 执行带 client、未撤销、未过期条件的 CAS，成功后在同一事务插入新 pair。
    • 只有事务 confirmed commit 才返回 Rotated；SQL/insert/commit 失败均为 StorageError。未知 COMMIT 结果不能当作 reuse，也不能向调用方返回任何新 token。
  • 撤销机制
    • 仅在 inspect 明确报告 AlreadyUsed 且能定位 family 时记录重用审计，调用 revokeTokenFamilyChecked。
    • checked revoke 提交确认后才算成功；成功则 invalid_grant，失败则 server_error，不会把存储故障伪装成“重用已处理”。
    • checked family revoke 撤销族内 RT 及关联 AT；旧 revokeTokenFamily 不再是刷新主路径。
    • ITokenRepository 新方法默认 fail closed；未实现 inspectRefreshToken / rotateRefreshToken 的旧自定义仓库会得到 StorageError，refresh 返回 server_error，不会回退到“撤销后签发”。

OIDC Discovery与JWKS端点的安全实现

  • Discovery端点
    • 提供issuer、各端点地址、支持的scopes/response_types/grant_types、id_token_signing_alg_values_supported等元数据。
    • 由DiscoveryController注册路由并描述OpenAPI。
  • JWKS端点
    • 返回当前用于签发JWT的RSA公钥集合（kty=RSA, use=sig, alg=RS256, kid）。
    • 由JwkManager提供keys数组。
  • 客户端验证步骤
    • 从JWKS获取对应kid的公钥，校验id_token签名，验证iss/aud/exp/nonce等claims。

上游 OIDC federation 的边界（未发布）

V045 upstream_providers 注册表 + 60 秒 runtime registry 支撑管理 CRUD /api/admin/upstream-providers 与 generic POST /api/auth/oidc/{provider}/login。legacy Google/微信/GitHub 行迁入 registry，但仍走各自协议实现。Keycloak 真实上游 E2E 脚本覆盖 authorize→上游登录→code exchange→userinfo→第一方 token pair；门户 generic OIDC 按钮/callback/exchange 尚未接通。

这不是完整 OIDC RP：当前 generic 只使用 token response 的 access token 调用 userinfo 并映射身份，不验证上游 id_token/JWKS/nonce，也不实现上游 PKCE。Fulla 自己作为 OP 的 Discovery/JWKS/RS256 id_token 能力不能拿来证明 upstream 验证已经完成。issuer 只允许 http(s) 前缀，不强制 HTTPS，也不构成 SSRF 防护。secret API 不回显不等于静态加密；registry listAll() 的 DB 错误会映射空列表，不能宣称故障保留旧快照。详见 [[authentication-security-social-login-security]]。

令牌缓存与 introspection 边界（未发布）

  • Redis token cache schema 提升为 2，access/introspection 序列化绑定 orgId；旧 schema 被拒绝，避免组织上下文丢失。
  • 安全读以 Postgres master 为权威来源，不用可能滞后的副本 refill L2；正缓存 TTL 不超过令牌剩余寿命。
  • refill 使用 Redis TIME 与绝对 expires-at，并通过 Lua 原子检查撤销 marker、绝对截止及 introspection 的 access-token 判别键；已过期快照不得回填。
  • 单次 lookup 只有 5 秒 steady-clock deadline，覆盖缓存查询、master read 与 guarded fill；截止后强制返回未命中/不活跃，不返回 stale positive。Redis 命令失败可读权威仓库，但不等于返回旧缓存。
  • 单 token revokeAccessToken 先完成权威撤销，再写 negative marker 并 double-delete access/introspection 正缓存；marker/DEL 为 best-effort，失败记日志/指标。族撤销不主动清所有正缓存，依赖 TTL 收敛，不能称全局即时撤销。
  • introspection 无有效结果时返回 HTTP 200 {"active":false}；只有 active 才附 client_id/token_type/exp/iat/nbf/sub/org_id/aud/iss/scope，所有响应 no-store。refresh-token introspection 不进入正缓存。
  • 非 memory 模式在 token active 后叠加 owner 状态：Active / Unmanaged 放行，Suspended / Unavailable 拒绝。owner 状态缓存 60 秒、查询 deadline 5 秒；超时、DB error、storage type 缺失均 Unavailable 且不缓存，NoRow 才是可缓存的 Unmanaged。
  • org_id 是令牌事实，不是实时组织成员资格；资源服务器仍需按 [[authorization-security]] 的组织与权限策略做实时决策。

性能考虑

  • PKCE验证
    • S256方法涉及一次SHA-256与Base64url编码，开销低；建议在令牌交换路径中尽早校验以减少后续处理。
  • 刷新令牌家族化撤销
    • 未发布轮换以 inspect、锁内重验、CAS 与同事务 pair insert 降低竞争；Memory 插入失败回滚，Postgres 仅 confirmed commit 返回 Rotated。checked revoke 也等待提交确认，未知 COMMIT 不误判 reuse、不泄露 token。
  • JWKS缓存
    • 客户端应缓存JWKS并按Cache-Control或固定周期刷新，降低网络与CPU消耗。
  • 连接池与索引
    • 刷新令牌家族化查询依赖family_id索引，确保高并发下性能稳定。

故障排查指南

  • 常见问题
    • PKCE验证失败：检查code_verifier格式与method是否匹配；确认S256哈希与Base64url编码一致性。
    • 刷新令牌重用：仅在确认 AlreadyUsed 且 checked family revoke 成功后记录并返回 invalid_grant；StorageError/未知 COMMIT 应返回 server_error，不记录为 reuse，不返回新 token。
    • introspection active 但 owner 不可用：检查 owner lookup 的 5 秒 deadline 与 60 秒缓存；Suspended/Unavailable 均拒绝，错误/超时不缓存。
    • 缓存旧 schema 或 orgId 缺失：确认部署已清空/迁移旧 token cache，避免回退到 schema=1。
    • JWKS缺失或kid不匹配：确认JwkManager初始化成功且kid与JWT header一致。
  • 定位步骤
    • 启用调试日志，关注令牌交换与撤销路径的错误码。
    • 使用脚本测试端到端流程（如test-oauth2-endpoints.sh）验证Discovery与JWKS可用性。
  • 参考命令
    • 运行后端OAuth2端点测试脚本，检查OIDC Discovery与JWKS返回内容是否符合预期。

结论

Fulla在OAuth2/OIDC安全方面实现了：

  • 完整支持授权码流程的 PKCE（仅 S256，v1.5.0 起；未发布 require_pkce 默认覆盖所有 authorization_code 客户端）。
  • RS256签名的JWT与标准的JWKS端点，便于客户端验证身份令牌。
  • 多方式客户端认证（Basic/Body参数），并为私钥JWT与公钥认证预留扩展空间。
  • 授权码流程强化（state、redirect_uri白名单、防重放）。
  • 刷新令牌家族化与未发布原子轮换/checked revoke，避免把存储故障误判为重用或泄露新 token。
  • 标准化的OIDC Discovery与JWKS端点，提升互操作性。

建议在生产环境中：

  • 配置持久化RSA私钥并定期轮换。
  • 严格校验state与redirect_uri，启用速率限制与审计日志。
  • 客户端缓存JWKS并校验kid/alg，拒绝none算法。
  • 遵循安全清单进行部署前检查与密钥轮换。
