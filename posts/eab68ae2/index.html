错误模型、重试与弹性策略

发表于2026-11-25|更新于2026-11-25|框架库Qt框架
|浏览量:
项目/qt-network-request/设计与架构
qt-network-request架构设计进阶

1. 定位与结论

本文回答三个运维与开发问题：库怎样判断成功、错误如何分类、失败后是否以及如何再次发送。核心结论：

  • 成功判定不是统一的“HTTP 2xx”：普通 HTTP 主要看 Qt 网络错误，下载类额外检查状态码，FTP 等路径需结合协议理解。
  • 错误模型已结构化，应使用 ErrorCategory + ErrorCode + nativeCode + message，不要解析自由文本。
  • 重试仅覆盖部分瞬态 Qt 网络错误，默认关闭；HTTP 4xx/5xx 本身不会触发当前重试逻辑。
  • 自动重定向只处理 301/302，沿用原方法和原 Body，不具备完整 HTTP 重定向语义。
  • 总超时、传输超时、idle 超时层次不同；Qt 5.6 兼容路径存在默认配置下传输超时可能不生效的问题。
  • 策略类已存在，但主管线尚未完全策略化；修改韧性行为时要同时检查具体请求子类。

2. 错误模型

定义见 include/networkerror.h:37-119：

类别 典型用途
None 无结构化错误
Cancelled 用户/管理器取消
Timeout 总时长、idle 或传输超时
Network 连接、DNS、远端关闭、代理等
Ssl TLS/SSL 握手或证书相关
Http HTTP 4xx/5xx
FileIo 打开、读取、写入、映射、重命名
Protocol 协议不支持、缺少长度等
Configuration URL、请求类型、认证配置错误
Unknown 无法归类的终止或异常

稳定错误码包括 OperationCancelled、TimeoutTotal/Idle/Transfer、ConnectionRefused、HostNotFound、RemoteHostClosed、TemporaryNetworkFailure、ProxyError、TooManyRedirects、SslHandshakeFailed、HttpClientError/ServerError、InvalidUrl、UnsupportedProtocol/RequestType、InvalidReply、ContentLengthMissing、认证错误及文件 I/O 错误等。

使用原则：

  • category 决定程序分支，code 决定细粒度处理，nativeCode 仅用于诊断 Qt 原始错误。
  • message 面向日志/UI，不应作为唯一判断条件；其中可能包含 URL 等敏感信息。
  • isSuccess() 等价于 !error.isError()，不独立检查 HTTP 业务码。

3. Qt 错误到库错误的映射

source/features/networkrequestutils.cpp:340-422 将常见 Qt QNetworkReply::NetworkError 映射为库级错误；HTTP 状态通过 makeHttpError 映射：

  • 400—499 → ErrorCategory::Http / HttpClientError。
  • 500—599 → ErrorCategory::Http / HttpServerError。
  • 其他状态不自动变成 4xx/5xx 错误。

需要注意：映射函数存在不代表所有请求子类都在所有路径调用它。是否最终返回 HTTP 错误取决于 evaluateOutcome() 和子类完成逻辑。

4. 成功判定

公共 evaluateOutcome() 见 source/requests/networkrequest.cpp:431-446：

含义：

  • 普通 NetworkCommonRequest 在 HTTP(S) 下拒绝 4xx/5xx。
  • 对 FTP，当前没有 HTTP 状态码可判定，主要依赖 Qt 网络错误。
  • 状态码通过 HttpStatusCodeAttribute 获取；没有 HTTP 状态时可能是 0。
  • MT 下载另有 Range/分片判定，不能仅依赖公共 helper，详见第 07 篇。

5. 响应体与 Header 收集

  • 仅成功路径调用 collectResponse() 收集 Header 和 Body；普通请求失败时通常丢弃错误响应体。
  • 下载类成功时将 Body 写入文件，结果 Body 通常为空。
  • Header 使用 QMap<QByteArray,QByteArray>；重复 Header 的保留方式受容器与 Qt rawHeader 行为影响，不应假设完整保留多值。
  • Cookie 可能通过 Jar 更新；结果中的 Cookie 字段不应被视为服务端 Set-Cookie 的完整审计日志。

6. 重试机制

实现见 source/requests/networkrequest.cpp:174-213。重试必须同时满足：

  1. 未因手动 abort 进入 m_isAbortedManually。
  2. behavior.retryOnFailed=true。
  3. 当前次数小于 maxRetryCount。
  4. Qt 错误属于瞬态集合。
  5. 具体子类允许清理后重启。

瞬态集合包括：

  • ConnectionRefusedError
  • HostNotFoundError
  • TimeoutError
  • OperationCanceledError
  • SslHandshakeFailedError
  • TemporaryNetworkFailureError
  • UnknownNetworkError
  • RemoteHostClosedError
  • TooManyRedirectsError

行为：

  • 中止并延迟删除当前 Reply，释放 NAM 引用。
  • 调用虚函数 cleanupForRetry() 清理子类资源。
  • 使用指数退避：retryDelayMs × 2^(retryCount-1)，上限 30 秒。
  • 通过 QTimer::singleShot 重新 start()，不增加全局工作线程。

6.1 不重试的典型情况

  • 默认未开启重试。
  • HTTP 4xx/5xx 状态本身不在瞬态 Qt 错误集合中。
  • 参数错误、文件打开失败、认证配置无效等本地错误。
  • 手动取消。
  • MT 下载的 Range 探测和分片阶段没有走完整重试路径；仅 HEAD 失败等少数路径可重试。
  • 达到最大重试次数。

6.2 重试的副作用

  • 单线程下载会关闭并重新创建/打开目标文件，从 0 重下。
  • 上传会关闭并重新打开源文件；源文件不会被库删除。
  • MT 下载清理后重建临时映射，不是断点续传。
  • 非幂等 POST/PUT 在连接中断后可能造成服务端重复处理；调用方需与服务端幂等键配合。
  • 退避期间请求仍占用工作执行槽，高并发下需考虑吞吐。

7. 自动重定向

实现见 source/requests/networkrequest.cpp:489-512：

  • 仅当 HTTP 状态为 301 或 302 且存在有效 RedirectionTargetAttribute 时尝试。
  • 使用当前 URL 解析相对目标。
  • 目标相同或超过 maxRedirectionCount 时不继续。
  • 删除当前 Reply、调用 cleanupForRetry()、修改 m_url 后重启请求。

当前限制：

  • 不处理 303、307、308 的完整方法语义。
  • 301/302 仍沿用原请求类型和原 Body，不自动把 POST 改成 GET。
  • 重定向后仍使用原认证/Header 配置；跨域跳转可能把凭据发往新主机，调用方必须评估。
  • API Key 如果位于 Query，重新构造 URL 时可能再次追加，需检查重复参数。
  • MT 下载重写 handleFailure() 以避免状态机被通用重定向破坏，其 Range 重定向能力不能按普通请求推定。

8. OAuth2 401 刷新

普通请求路径在以下条件同时满足时自动刷新一次：

  • HTTP 状态为 401。
  • 认证类型为 OAuth2。
  • 配置中已有 refresh token。
  • m_isOAuthRefreshed 尚未置位。

实现将 grant 临时切换为 RefreshToken，清理 Reply，再调用 start() 触发 Token 预取。限制：

  • 每个请求最多自动刷新一次，没有无限循环。
  • 只在已有 refresh token 时工作；ClientCredentials 的 401 不会走此刷新。
  • OAuth2 预取只在 NetworkCommonRequest 中实现；上传、下载、MT 下载不能假定具有相同行为。
  • 新 refresh token 写入缓存，但没有回填当前 AuthConfig，后续请求依赖缓存与 grant 状态。
  • Token 缓存键不包含密码、client secret 或 refresh token 内容，存在不同凭据复用同键的边界问题，详见第 08 篇。

9. 三层超时

超时 配置字段 起点 当前实现
总超时 behavior.totalTimeoutMs / Builder .timeout() Runnable 开始执行 worker QTimer，CAS 保证一次性终态；不含排队
传输超时 behavior.transferTimeout 请求准备/Reply 阶段 Qt ≥5.15 使用 QNetworkRequest::setTransferTimeout；旧 Qt 用心跳 fallback
idle 超时 behavior.idleTimeoutMs 请求开始后按 250ms 心跳累计 数据到达重置计数；阈值为 idleTimeoutMs / 250

9.1 Qt <5.15 的兼容风险

QtCompat::setTransferTimeout() 在 Qt <5.15 是空操作，startTransferTimer() 只启动 QElapsedTimer。fallback 的检查位于 NetworkRequest::onHeartbeat()，而心跳启动逻辑与 idleTimeoutMs > 0 相关。默认 idleTimeoutMs=0 时，存在 transfer timeout 计时器已启动但心跳不运行、超时不生效的路径。

这不是“所有旧 Qt 都一定失效”的运行结论，而是需要专项验证的静态风险。Qt 5.6.3 兼容目标下应优先补测试，而不是仅依赖默认 transferTimeout=30000。

9.2 总超时与取消

  • 总超时胜出时发送 Timeout / TimeoutTotal，nativeCode 使用 Qt TimeoutError。
  • 总超时不会删除文件或恢复已写数据；文件残留按具体传输路径处理。
  • 手动取消与超时在 Runnable 中可能统一修正为取消，但已明确分类为 Timeout 的结果不会被改成 Cancelled。

10. 策略类与主管线

source/infra/requeststrategies.h 与 source/infra/requeststrategies.cpp 已定义：

  • IRetryStrategy / DefaultRetryStrategy
  • IRedirectHandler / DefaultRedirectHandler
  • ISslPolicy / DefaultSslPolicy

但当前重试、重定向和 TLS 决策仍在 NetworkRequest 中直接实现。策略类目前不能视为完整可替换扩展点。若要修改行为，应同时检查：

  • NetworkRequest::tryRetry/handleFailure
  • 具体子类是否重写 handleFailure/cleanupForRetry
  • Runnable 的 abort/总超时路径
  • Manager 停止路径

11. 失败矩阵

失败源 默认结果 是否重试 文件影响
非法 URL Configuration/InvalidUrl 否 通常尚未创建
无法创建/打开文件 FileIo/FileOpenFailed 否 单线程可能无文件；MT 映射失败
连接拒绝/DNS/远端关闭 Network 对应错误码 仅显式开启且属瞬态集合 下载重试从头开始
HTTP 4xx HttpClientError 否 普通请求无错误 Body；下载删除文件
HTTP 5xx HttpServerError 否（仅 Qt 网络错误触发重试） 同上
301/302 自动跳转或最终 HTTP 错误 按重定向计数 下载可能重新创建文件
TLS 失败 SslHandshakeFailed 可重试，但默认关闭 取决于请求类型
总超时 Timeout/TimeoutTotal 不再次重试 可能留下部分文件
idle 超时 Timeout/TimeoutIdle 具体路径决定 可能留下部分文件
手动取消 Cancelled/OperationCancelled 否 单线程可能残留，MT 通常删除临时文件

12. 注意事项

  1. 程序分支使用结构化错误，不解析 message 中的英文片段。
  2. 对非幂等请求谨慎开启自动重试。
  3. 不要把“重试次数 3”理解为“总共发送 3 次”；当前语义是最多额外重试 3 次。
  4. 不要把 301/302 当作完整 RFC 重定向实现。
  5. 跨域重定向、Query 中 API Key、认证 Header 需要安全审查。
  6. 日志中的完整 URL、认证挑战响应体和 TLS 错误可能泄露敏感信息。
  7. 失败响应体为空不一定是 Qt 没读到，而是当前收集逻辑只在成功时执行。
