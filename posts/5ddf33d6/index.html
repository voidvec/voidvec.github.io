系统架构：模块划分、请求路由与数据所有权

发表于2026-11-25|更新于2026-11-25|框架库Qt框架
|浏览量:
项目/qt-network-request/设计与架构
qt-network-request架构设计进阶

1. 系统定位

QtMultiThreadNetwork 是一个 C++14 的 Qt Network 封装库，用线程池执行 HTTP(S)/FTP 请求，提供统一 Builder、异步结果、进度、取消、重试、下载/上传和 MT 下载能力。仓库同时包含：

  • 一个共享库：QNetworkRequest。
  • 两个示例 GUI：QtRequester、QtDownloader。
  • 一个测试目录：Qt Test 多可执行测试集。
  • 构建/打包/CI 脚本，以及 Conan/vcpkg 集成草案或入口。

它不是独立网络服务，不包含服务器端业务、账户系统、数据库或云控制面。业务边界主要是“客户端发起传输并管理本地文件/请求资产”。

2. 系统上下文

外部依赖边界：

  • Qt：Core、Network 是库的主运行依赖；Widgets、Xml、Test 因示例、测试及当前 CMake 查找方式进入构建图。
  • OpenSSL：HTTPS 的运行支撑；Windows 复制 DLL，Unix 配置查找/链接。
  • 本地文件系统：下载目标、上传源、MemoryMappedFile、Cookie、请求资产和 QSettings。
  • 外部网络服务：由调用方 URL 决定，库不限定业务 API。
  • 示例资源：图标、QSS、UI 文件通过 qrc/UIC 进入示例，不属于核心库运行必需项。

3. 构建目标与代码边界

CMake 定义以下主要目标：

目标 来源 性质
QNetworkRequest source/ + include/ 唯一核心共享库
QtRequester samples/networkrequesttool/ 请求工具 GUI
QtDownloader samples/networkdownloader/ 下载队列 GUI
九个测试可执行 test/ Qt Test，部分 GUI/无头

关键事实：

  • add_library(QNetworkRequest SHARED ...) 固定为共享库，CMake 无静态库开关，见 source/CMakeLists.txt:5。
  • source/ 下所有实现编译进同一个库；core/requests/features/infra 是逻辑分层，不是独立部署单元。
  • 库只私有链接 Qt::Core 与 Qt::Network，见 source/CMakeLists.txt:90-93。
  • 根 CMake 无论 BUILD_SAMPLES/BUILD_TESTS 是否关闭，都先查找 Widgets/Xml/Test，见 CMakeLists.txt:24-53。
  • QMake 支持 staticlib，Debug 产物为 QNetworkRequestd；CMake Debug 产物仍为 QNetworkRequest，输出到 build/<Config>。两套构建的布局不能混用。

4. 逻辑模块

4.1 公共契约层 include/

  • 请求输入：RequestContext、Builder、TaskData、认证/代理/TLS/上传/下载配置。
  • 输出：ResponseResult、ErrorInfo、NetworkReply。
  • 生命周期入口：NetworkRequestManager。
  • 资产：Environment、EnvironmentStore、CollectionModel、PostmanConverter、OAuth2TokenCache。

职责：向调用方表达数据、默认值、所有权和可用操作，不暴露线程池、NAM 池、状态机等私有实现。

4.2 调度与并发层 source/core/

  • NetworkRequestManager：全局生命周期、ID、映射、停止、进度、结果转发。
  • NetworkRequestRunnable：线程池执行单元、局部事件循环、总超时、一次性终态。
  • NetworkAccessManagerPool：线程亲和 NAM 池。
  • NetworkRequestRegistry：按请求类型和优先级创建 Request。
  • NetworkReply：对外结果句柄。
  • ProgressThrottle：进度限流。

依赖方向：Manager 管 Runnable/映射；Runnable 通过 Registry 找 Request；Request 从 NAM 池获取网络设施；结果经 Manager 返回调用方。

4.3 请求执行层 source/requests/

  • NetworkRequest：公共基类，封装 NAM、请求准备、认证 Header、TLS、重试、重定向、超时和结果构造。
  • NetworkCommonRequest：GET/POST/PUT/DELETE/HEAD/PATCH/OPTIONS，含 OAuth2 Token 预取。
  • NetworkDownloadRequest：单线程流式写文件。
  • NetworkUploadRequest：文件/multipart 上传。
  • NetworkMTDownloadRequest + _states.cpp：HEAD/Range 探测、分片、映射、重命名。

路由不是按类名硬编码，而是各 .cpp 在静态初始化时向 Registry 注册 creator；普通方法优先级 5，显式 MTDownload 优先级 10，自动 MT 下载由条件路由胜出。

4.4 基础设施层 source/infra/

  • MemoryMappedFile：Windows/Unix 文件映射封装。
  • PersistentCookieJar / SharedCookieJar：文件持久化与线程 NAM 共享包装。
  • requeststrategies：重试、重定向、SSL 策略接口与默认实现；当前未完全接入主管线。

4.5 功能层 source/features/

  • networkrequestutils：请求类型字符串、文件创建/打开、Qt/HTTP 错误映射等。
  • environment：{{key}} 变量替换。
  • environmentstore：命名环境 JSON 显式存取。
  • oauth2tokencache：Token 缓存。
  • collectionmodel：文件夹/请求树。
  • postmanconverter：Postman v2.1 部分字段映射。

4.6 Qt 兼容层 source/core/qtcompat.h

集中处理 Qt 版本差异：transfer timeout、error/errorOccurred、HTTP/2 属性、TLS 1.3、递归 mutex、QList::reserve、SkipEmptyParts、QThreadPool::tryTake、sendCustomRequest、UUID 格式等。示例中仍有零散 #if QT_VERSION，不能说全仓库版本分支都已集中。

5. 请求路由关系

补充规则：

  • Unknown 或没有匹配 creator 时返回空 Request，Runnable 生成 UnsupportedRequestType。
  • 显式 MTDownload 优先级高于普通注册项。
  • 自动 MT 的 threadCount=0 先取 CPU 数，再受 Range 探测结果影响。
  • Registry 当前没有运行时并发锁，动态扩展不在已验证安全范围内。

6. 数据流与所有权

  • Context 使用 unique_ptr 单向移交。
  • Result 使用 QSharedPointer 跨线程传递。
  • 对外 Reply 使用 std::shared_ptr，Manager 与调用方共同持有。
  • NAM 由池所有，Request 只持非拥有引用。
  • Cookie 全局 Jar 由 Manager 所有，线程 NAM 通过 SharedCookieJar 包装共享。
  • 文件映射和临时文件的所有权属于具体传输请求，停止/异常路径需要分别审计。

7. 核心业务流程

  1. 普通请求：Builder → postRequest → worker → CommonRequest → Qt Reply → 成功/失败 Result。
  2. 单线程下载：Builder → DownloadRequest → 最终文件流式写入 → 成功保留/失败删除。
  3. 上传：Builder → UploadRequest → 只读源文件/multipart → Qt POST/PUT/FTP PUT → 关闭文件。
  4. MT 下载：Builder → HEAD → 可选 0-0 Range 探测 → 单/多通道 → 同文件 mmap 随机写 → rename。
  5. 认证与环境：公共请求路径做认证 Header 和 {{key}} 替换；OAuth2 Token 预取目前仅在 CommonRequest。
  6. 请求资产：GUI 显式保存环境/集合/请求 JSON；公共库提供数据模型和转换，不自动管理 UI 文件。
  7. 取消/超时：Manager/Runnable/Request 多层协作，终态是否可见取决于停止 API；文件状态取决于请求类型。

8. 设计意图与当前实现的差异

docs/refactor-network-request-design.md 是 2026-07-27 的设计草案，提出注册表、策略、状态机、分层错误等方向。当前已落地：

  • 请求注册表替代硬编码创建。
  • 结构化错误。
  • MT 下载状态机。
  • 共享 helper 和 QtCompat。
  • 默认策略类。

尚未完全落地或不能直接按草案推断：

  • 主管线仍直接调用重试/重定向逻辑，策略未完全注入。
  • 草案中的部分路径、阶段和完成状态可能已变化。
  • 状态机完善不等于 Range 完整性校验已实现。
  • Changelog 的版本能力声明不等于所有请求类型都已接入，例如 OAuth2 预取。

因此，架构维护应遵循“当前源码 > 当前构建配置 > 现行 README > Changelog > 历史设计草案”的证据顺序；冲突时显式记录而不是静默合并。

10. 边界约束

  1. 库是共享库架构，但 CMake 安装导出未携带 Qt 依赖，独立消费者需自行 find_package(Qt...)。
  2. 线程安全不是全局无条件成立：对象亲和、Registry 和全局 proxy/Cookie 配置存在边界。
  3. MT 下载的“多线程”是同一 worker 上多个异步 Range 通道。
  4. 文件传输没有内容哈希、ETag 验证或通用断点续传契约。
  5. Postman 支持是部分字段映射，不是 v2.1 无损转换。
  6. 示例是能力演示，不是所有公共配置的完整 UI 覆盖；部分字段没有接线或存在缺陷。
  7. HTTPS 能力依赖 Qt/OpenSSL 与平台运行时部署，不能仅凭编译成功推定握手成功。
  8. 测试当前以本地 HTTP 为主，真实 TLS、FTP、Qt6、旧 Qt 和大文件矩阵尚未闭环。
