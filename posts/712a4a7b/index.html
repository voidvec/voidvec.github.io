简介

本文件面向Fulla的安全加固，覆盖输入验证与清理（SQL注入、XSS、命令注入）、依赖包安全更新与漏洞扫描、敏感信息保护（配置与密钥管理、日志脱敏）、安全审计与监控、安全配置基线、渗透测试与安全评估流程，以及安全事件响应与漏洞修复指南。“配置加密”在本页仅指可采用的部署控制，除非代码明确提供，否则不把环境变量、不回显 API 或外部 Secrets 注入等同于静态加密。

项目结构

本项目将安全能力分布于多个层次：

  • 应用层：全局安全头注入、速率限制、CORS策略、错误标准化与统一响应体。
  • 业务层：认证授权、客户端鉴权、密码重置/修改、RBAC与Scope校验、审计事件写入。
  • 数据层：迁移脚本、存储后端（Postgres/Redis/Memory）的敏感数据存储策略。
  • 基础设施层：CI/CD安全门禁（依赖EOL检查、敏感文件扫描）、容器化部署与密钥挂载。
  • 前端层：安全测试用例（XSS、注入）、构建时环境变量内联、运行时安全头配合。

核心组件

  • 输入验证与清理
    • 后端集成测试覆盖SQL注入、XSS、命令注入与长度限制等场景，确保非法输入被拒绝或清洗。
    • 前端E2E用例对登录用户名注入与XSS渲染进行断言，保证前端侧不执行恶意脚本。
  • 安全响应头
    • 通过全局后置处理在所有响应中注入安全头；HTML页面启用严格CSP，仅在 X-Forwarded-Proto 精确为 https 时下发HSTS。
  • 速率限制
    • 针对登录、令牌颁发、注册等高价值接口实施细粒度限流，防止暴力破解与DoS。
  • 审计与可观测性
    • 关键操作（如密码修改、密码重置）均记录结构化审计事件，包含主体、目标、结果、IP、UA、请求ID等。
  • 依赖与供应链安全
    • CI定时与触发式运行依赖EOL检查，阻断已知不安全版本；仓库级敏感文件扫描避免凭证泄露。
  • 密钥与配置安全
    • JWT签名密钥支持从文件系统加载并持久化，环境变量覆盖敏感配置；生产模式强制校验。

安全响应头与CSP/HSTS

  • 全局后置处理为所有响应添加安全头；HTML页面启用严格CSP，API端点不受影响。
  • 仅在 X-Forwarded-Proto 精确为 https 时设置HSTS；不调用 req->isSecure()，直接TLS连接不会自动触发应用层HSTS。

速率限制与暴力破解防护

  • 对登录、令牌、注册等敏感接口实施每IP/每用户/全局多维限流，返回429并走统一错误体。
  • 识别策略（Hodor 通用限流）：优先X-Forwarded-For，其次X-Real-IP，最后Peer IP；白名单跳过限制。
    • 登录失败限流例外（v1.2.0）：默认仅按 TCP peer 键控，auth.rate_limit_trust_forwarded_for 显式设 true 才信任 XFF（生产布局因 nginx 前置已开启）；失败登录额外烧一次 PBKDF2 以拉平 miss/锁定/策略拒绝的时序。

敏感信息保护（配置、密钥管理与日志脱敏）

  • 密钥管理：JWT 签名密钥支持从文件系统加载并持久化，开发模式回退临时密钥；密钥路径通过环境变量配置。生产部署应保护文件权限并轮换。
  • 配置安全：支持环境变量覆盖敏感项（数据库、Redis、Issuer、监听端口等）及生产模式校验；这些机制本身不证明配置或 upstream client_secret 在静态存储时已加密。
  • upstream secret（未发布）：管理 API 创建时接收 secret、列表/详情不回显，更新可省略以保留旧值；写入-only 仅防止回显，数据库静态加密需另行验证或由部署层提供。
  • 日志脱敏：不在日志输出 client_secret/token；审计仅记录必要上下文。部署还应限制数据库备份、Helm values 与镜像构建参数的访问。

安全配置基线（生产环境模板与自动化检查）

  • 生产模式校验：Fulla 自身 Issuer/回调与非默认数据库密码等按生产模板校验；未发布 generic upstream issuer 允许 http:// 或 https://，不能套用“上游必须 HTTPS”的结论。
  • 环境变量覆盖：集中管理敏感配置，避免硬编码；外部注入不等于数据库静态加密。
  • 自动化检查：CI 与本地脚本降低敏感文件泄露风险，但不能替代运行时出站控制。
  • generic upstream 出站（未发布）：当前仅做 HTTP(S) scheme 校验，尚未证明 SSRF 防护；部署需自行限制目的地、DNS 解析、内网地址、重定向与 egress，不能宣称 registry 已解决 SSRF。

渗透测试与安全评估流程

  • 建议流程
    • 代码阶段：静态扫描、依赖EOL检查、单元测试与属性测试。
    • 集成阶段：端到端安全测试（注入、XSS、越权、速率限制）。
    • 预发布：外部扫描（依赖漏洞、容器镜像SBOM）、合规检查（OpenAPI差异、规范校验）。
    • 上线后：持续监控（审计日志、异常告警）、周期性复测。

    • CI：security.yml、dependency_eol_check.py、security-check.sh。

安全事件响应与漏洞修复指南

  • 报告渠道：通过GitHub私有漏洞报告通道提交，避免公开披露。

2026-09 审计 P0/P1 加固清单（v1.2.0）

增量补篇：v1.2.0 落地 2026-09 逐行后端安全/正确性审计的 P0 批（46 项发现，独立复核；其余加固项在后续 PR 继续）。以下为安全相关要点，逐条对应 CHANGELOG.md [1.2.0] Security 段。

  • 授权码签发守卫（审计 P0-4）：login/consent/MFA/device 四条路径此前不经 /oauth2/authorize 边界即可铸造授权码——共享签发守卫现在统一校验客户端存在、redirect_uri 已注册、scope 在客户端白名单内（关掉”认证型开放重定向”）；code_challenge 格式按 RFC 7636 §4.2 校验；MFA verify 把守卫失败映射为其冻结的通用 401 契约（防枚举）。
  • 独立 Redis 授权存储对齐（审计 P0-5）：Redis 后端的 code 存储此前丢失 code_verifier 对、nonce 与认证上下文，且请求侧为空时跳过 redirect_uri 匹配；语义对齐 Postgres 存储（PKCE/nonce/redirect_uri 一致）。
  • OIDC nonce 落库（审计 P0-1）：V032 为 oauth2_codes 增加 nonce 列；nonce 在签发时持久化并在兑换的 id_token 中回显（修复 id_token.nonce 永远为空、code 流重放检测失效）。
  • GET /config.json 不再回显凭据（审计 P1-15）：静态文件服务此前直接吐出服务端自身配置（开发/生产布局下含 DB/Redis 凭据）；所有随附配置关闭 allow_all 并将 file_types 收窄到无害资产。
  • URL 查询串 Bearer 拒绝（RFC 9700）：拒绝以 URL 查询参数携带的 Bearer 令牌。
  • CORS 收紧：异常处理器不再对任意 Origin 回显凭据（去掉任意 Origin + 凭据组合），并输出 Vary: Origin。
  • CSPRNG 失败不再产生确定性令牌：安全随机源失败时不再回落到可预测路径铸造令牌。
  • RSA < 2048 位密钥拒绝。
  • **跨客户端兑换授权码返回 invalid_grant**。
  • **refresh 令牌内省不再伪造 iat/nbf**。
  • 未知 token_endpoint_auth_method fail-closed：无法识别的客户端认证方法按失败处理，而非放行。
  • 同批伴随项（详见 [[authentication-security-password-security]]）：失败登录烧一次 PBKDF2 拉平时序、登录失败限流默认按 TCP peer 键控（auth.rate_limit_trust_forwarded_for 显式开启才信 XFF）。

未发布加固摘要

  • require_pkce 替换旧键，默认所有 authorization_code 客户端 S256；代码签发 redirect 未注册为 3027，end_session 为 3013。
  • 社交 state 改为服务端一次性状态：Redis 仅存 SHA-256 digest，SET NX EX 600 + Lua compare-delete，Cookie 绑定 provider/redirect，Redis 故障 fail closed。
  • 刷新采用 inspect → 锁内重验 → 原子轮换 pair；Postgres 仅 confirmed commit 返回 Rotated，未知 COMMIT 不误判 replay，旧自定义 ITokenRepository 默认 fail closed。
  • 令牌缓存 schema=2、org 绑定、绝对截止、Redis TIME/撤销 marker 原子 refill、本地 5 秒 deadline、无 stale fallback；族撤销仅靠 TTL 收敛，不是全局即时。
  • introspection active-only/no-store，owner Suspended/Unavailable 拒绝且错误不缓存。详细边界见 [[oauth2-oidc-security]]。

性能考虑

  • 速率限制在高并发下需关注内存占用与键空间膨胀，建议合理设置过期时间与采样策略。
  • 审计日志异步写入，避免阻塞主请求路径；注意磁盘I/O与索引优化。
  • 安全头注入为轻量操作，但CSP规则过严可能影响第三方资源加载，需按需放宽。

故障排查指南

  • 常见现象
    • 登录/注册频繁429：检查Hodor限流配置与白名单。
    • 浏览器拦截资源：检查CSP策略与外部资源域名。
    • HSTS未生效：确认 X-Forwarded-Proto 精确为 https；后端不检测直接TLS，Nginx需自行配置HSTS。
    • 审计缺失：确认审计Sink已注入且写入成功。
  • 诊断步骤
    • 使用curl检查响应头与错误体。
    • 查看审计日志与管理后台。
    • 检查CI安全门禁失败原因（依赖EOL、敏感文件）。
    • 核对环境变量覆盖与生产模式校验结果。

结论

Fulla在输入验证、安全头、速率限制、审计、依赖治理与密钥管理方面已形成较为完善的安全体系。建议在后续迭代中持续强化：

  • 扩大注入与XSS的自动化测试覆盖与模糊测试。
  • 完善审计事件的聚合分析与告警规则。
  • 建立常态化渗透测试与红蓝对抗演练。
  • 持续跟进依赖漏洞与供应链安全。
