文件上传与下载

AR##-进阶
发表于2026-11-25|更新于2026-11-25|框架库Qt框架

项目/qt-network-request/设计与架构
qt-network-request架构设计进阶

1. 定位与结论

本文覆盖 NetworkUploadRequest、NetworkDownloadRequest 及二者共用的文件命名/打开逻辑。MT 下载状态与 Range 契约见第 07 篇。核心结论：

  • 单线程下载直接写最终文件，不使用临时文件；网络/协议失败会删除，但取消和部分超时路径可能留下不完整文件。
  • 单线程下载的短写/写失败只记录错误，最终仍可能报告成功；没有哈希或长度完整性校验。
  • 上传只读打开源文件，成功或失败都不删除源文件；重试会关闭并重新打开。
  • UploadConfig::data 只用于字节估算，useStream 当前未使用；非 multipart 实际发送的是 filePath 指向的文件。
  • 上传没有走公共 prepareRequest()，因此不能假定 queryParams、认证配置、BodyType Content-Type 与普通请求完全一致。
  • 默认文件名会清理部分危险字符，但显式 saveFileName 没有等价 basename/路径穿越校验；调用方必须信任并校验该输入。

2. 请求类型选择

Registry 路由规则：

  • RequestType::Upload → NetworkUploadRequest。
  • RequestType::Download 且 threadCount=1 → 单线程 NetworkDownloadRequest。
  • RequestType::Download 且 threadCount>1 或 0 → MT 下载。
  • 显式 RequestType::MTDownload → MT 下载。

threadCount=0 的“自动”不等于单线程；没有 Range 能力时才回退为单通道，但仍使用 MT 临时文件/映射路径。

3. 文件命名与目录

公共逻辑位于 source/features/networkrequestutils.cpp:39-201：

  1. 下载目录来自 downloadConfig.saveDir；具体路径规范化由工具函数完成。
  2. 文件名优先使用显式 saveFileName。
  3. 未指定时从 URL query 中的 response-content-disposition / content-disposition 提取 filename=。
  4. 再回退到 URL 文件名。
  5. 从 query Content-Disposition 提取时会移除 " : < > | / \\ 等字符。

边界与风险：

  • 显式 saveFileName 直接返回，没有再执行 basename 或 .. 清理，可能突破预期目录；应仅在可信输入下使用。
  • URL query 文件名清理不是完整的 RFC 5987/6266 解码，也不处理全部字符集与扩展参数。
  • 文件名为空会失败。
  • 单线程和 MT 对同名文件处理不同，见下表。
场景 单线程下载 MT 下载
目标不存在 创建最终文件 创建 UUID 临时文件，成功后 rename
目标存在，overwriteFile=false 直接冲突失败 自动尝试 _1…_99 后缀
目标存在，overwriteFile=true 先删除旧文件再创建 先选路径；rename 前删除已有目标
后缀全部占用 不适用 getFilePath() 可能返回原已存在路径，rename 阶段再失败

MT 的“自动后缀”与单线程“冲突失败”是实际行为差异，不应只依据 overwriteFile 字段推断。

4. 单线程下载主流程

source/requests/networkdownloadrequest.cpp:49-125,127-214：

4.1 数据与性能

  • 流式读取并写入，不把整个响应保存在内存。
  • m_bytesReceived 在完成时被赋值为 m_bytesWritten，不是 Qt 报告的总接收字节。
  • 下载 Result 的 Body 通常为空；文件内容通过目标路径获取。
  • 进度来自 QNetworkReply::downloadProgress，经 ProgressThrottle 限流后投递 Manager。
  • 没有 Content-Length 时进度百分比可能无法计算；当前回调直接使用 bytes * 100 / total，应确认 total>0 的上游条件。

4.2 文件状态矩阵

事件 文件处理 结果
URL 非法 尚未创建 Configuration/InvalidUrl
同名冲突且不覆盖 不创建 FileOpenFailed
打开失败 无有效文件 FileOpenFailed
网络失败/HTTP 4xx/5xx CloseFile(true) 删除 失败
301/302 重定向 子类 cleanupForRetry() 关闭/删除后重启 中间结果不暴露
显式重试 从头创建/写 可能覆盖同一次下载的部分文件
写返回 -1 设置 FileWriteFailed，但不主动 abort 后续成功路径会清空 error，可能报成功
短写 只记录 expected/wrote 不补齐、不失败
手动 abort/定向停止 abort 删除 Reply 并阻断信号，通常不走 finished 清理 可能留下部分最终文件
总超时 Runnable 发超时并退出；文件清理不保证 可能留下部分最终文件
idle/legacy transfer 超时 abort 路径，清理不一定执行 可能留下部分最终文件
进程崩溃/断电 无恢复机制 留下部分文件

“可能留下”是静态路径判断，不是运行测量。取消 API 是否补发终态见第 04 篇。

4.3 完整性与断点

当前没有：

  • ETag / If-Match / If-Range。
  • 内容哈希或期望长度校验。
  • .part 元数据或已下载区间记录。
  • 自动断点续传。

因此文件存在、大小看似正确或进度到 100%，都不能单独证明内容完整。

5. 上传主流程

source/requests/networkuploadrequest.cpp:49-223：

  1. 校验 URL。
  2. 获取线程 NAM，应用 proxy，插入请求 Cookie。
  3. 直接构造 QNetworkRequest，设置 transfer timeout、默认 application/octet-stream 和自定义 Header。
  4. 根据 useFormData && files非空 决定 multipart；否则打开 filePath。
  5. HTTP(S) 按 usePutMethod 选择 PUT/POST；FTP 强制 PUT。
  6. 发送 Reply，连接完成、错误、认证挑战和可选上传进度。
  7. 完成时关闭文件，判定结果，成功收集响应。

5.1 源文件所有权

  • 非 multipart：NetworkRequestUtils::openFile() 以只读方式打开。
  • multipart：每个文件以只读 QFile 打开并挂到 QHttpMultiPart。
  • CloseFile() 只关闭并释放库内句柄，不删除源文件。
  • 重试时 cleanupForRetry() 关闭源文件；下次 start() 重新打开。
  • 如果上传期间源文件被外部截断/修改，当前没有快照或哈希校验。

5.2 配置字段实际语义

字段 当前行为
filePath 非 multipart 的实际数据源；也用于初始字节估算
data 只参与 m_bytesSent 估算，不作为实际上传 Body
useStream 当前上传实现未使用
useFormData 只有同时 files 非空才进入 multipart
files 不存在或打不开的文件直接跳过，不使整个请求失败
kvPairs 转为 multipart 文本字段
usePutMethod HTTP(S) 选择 PUT/POST；FTP 忽略该选择，始终 PUT

风险：

  • uploadConfig 是必要边界，当前使用 Q_ASSERT 后直接解引用；Release 下不能依赖断言保护，调用方必须提供有效配置。
  • multipart 全部文件被跳过且 kvPairs 为空时，仍可能发送空 multipart。
  • multipart 文件字段名固定为 file，重复文件没有独立字段名规则。
  • FTP multipart 会把 QHttpMultiPart 交给 FTP PUT，真实协议行为未验证，不应视为已证明能力。

5.3 与普通请求的配置差异

上传没有调用 prepareRequest() / applyAuthConfig() / applyBodyTypeContentType()，因此：

  • queryParams 和 API Key Query 不会按普通请求路径追加。
  • Basic/Bearer/OAuth2/API Key Header 认证配置不会按普通请求路径注入。
  • environment 的 URL/Header/文本 Body 替换不能据此假定覆盖上传。
  • 调用方若需认证，必须自行提供有效 Header，并确认其与认证配置的一致性。
  • 默认 Content-Type 为 application/octet-stream，multipart 路径会覆盖为 multipart boundary。

这与第 08 篇“认证 Header 注入”并不矛盾：该 helper 只有被具体请求路径调用才生效。

6. 取消、重试与失败

  • 手动 abort 不重试。
  • 显式开启重试且 Qt 错误属于瞬态集合时，关闭源文件后从头发送。
  • HTTP 4xx/5xx 不触发当前重试。
  • 对非幂等上传，重试可能造成服务端重复写入；应配合幂等键或关闭重试。
  • 失败时只返回结构化错误和成功路径下的响应体，不保留部分上传文件。
  • 源文件不会因取消、失败或重试被删除。

7. MemoryMappedFile 平台语义

虽然 MT 下载是主要使用者，文件映射的公共语义影响所有大文件传输，见 source/infra/memorymappedfile.cpp:25-269,357-384。

方面 Windows Unix（Linux/macOS）
创建 CreateFileW(CREATE_ALWAYS) open(O_RDWR|O_CREAT|O_TRUNC)
扩展 SetFilePointerEx + SetEndOfFile ftruncate
映射 CreateFileMappingW + MapViewOfFile mmap(MAP_SHARED)
写入 memcpy 到映射视图 同
flush FlushViewOfFile msync(MS_SYNC)
关闭 Unmap/CloseHandle munmap/close

注意：

  • Unix ftruncate 设置逻辑长度，不保证物理块预分配；磁盘满可能在写入/同步阶段暴露。
  • size 为 qint64，代码尝试支持 >4GB；Windows 映射参数拆成高低 32 位，Unix 使用 size_t。实际受平台位数、地址空间、文件系统和 Qt 构建影响。
  • write() 有 mutex 并会把越界请求截到文件末尾；writeUnsafe() 明确无锁。
  • flush() 返回值在 MT 分片完成路径被忽略，不能据此证明已持久化成功。
  • open() 已持有 QMutex 后调用同样加锁的 close()；同一对象在已打开状态下重复 open 存在自锁死锁风险。正常 MT 路径新建对象，未触发不代表安全。
  • 头文件“自动预分配”“支持 >4GB”是设计声明，需按平台实测。

8. 安全与运维注意事项

  1. 显式 saveFileName 必须由调用方限制为 basename，拒绝绝对路径、分隔符和 ..。
  2. 覆盖现有文件是破坏性操作；单线程会在下载开始前删除，MT 会在 rename 前删除。
  3. 日志中的完整 URL 和文件路径可能包含 Query 凭据或敏感目录。
  4. Cookie、环境、请求 JSON 可能含明文凭据，下载目录不应放在不可信共享位置。
  5. 不对结果文件做校验时，业务侧应按需在下载后验证大小/哈希/签名。
  6. 磁盘满、只读目录、rename 跨文件系统、文件被占用等需要真实平台测试。
