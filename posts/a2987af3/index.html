运行、配置与 Windows 打包

qt-network-request数据与运维进阶

1. 定位与结论

本篇是本地运行和发布排障入口，不重复 Builder/请求语义。核心结论：

  • 两个示例都是桌面 GUI，不是无界面服务；库本身没有独立 main 或常驻进程。
  • NetworkRequestManager 必须在主线程初始化/反初始化；两个示例分别在主窗口或 Manager 构造/析构中管理。
  • QtRequester 的请求资产与凭据保存在 AppDataLocation/requests 下的 JSON，认证信息明文；下载器设置和任务使用 QSettings。
  • Windows 本地可执行文件依赖同目录/PATH 中的 Qt、OpenSSL 和主库 DLL；打包脚本才调用 windeployqt。
  • CMake 安装导出不等于可运行发布包；Qt 运行时、OpenSSL、平台插件和许可证需另行部署。
  • Windows MSI 链当前存在确定阻塞：pack 校验 QtRequester.exe/QtDownloader.exe，WXS 却 harvest QtNetworkRequestTool.exe/QtNetworkDownloader.exe。
  • 版本号分散在 CMake、Changelog、Conan、vcpkg、MSI 和应用元数据中，尚无单一发布事实源。

2. 运行入口与生命周期

QtRequester

samples/networkrequesttool/main.cpp:7-22：

  1. 设置高 DPI；
  2. 创建 QApplication、应用图标；
  3. 在显示任何窗口前恢复主题；
  4. 构造主窗口并进入事件循环。

networkrequesttool.cpp:89-138 中主窗口初始化公共库、UI、环境和集合；析构调用 unInitialize()。运行时可从“设置”配置代理、超时、重试，再从 URL/Params/Headers/Body/Auth 构造请求。

QtDownloader

samples/networkdownloader/main.cpp:5-27：QApplication、高 DPI、组织名 QtDownloader、应用名 Qt Downloader、版本 1.0、主题、主窗口。

downloadmanager.cpp:10-25,27-50：Manager 构造时初始化公共库、加载设置和任务，默认目录为 ~/Downloads；析构清理活动引用并反初始化。主窗口另用 QSettings("QtDownloader","MainWindow") 保存窗口几何/状态（downloadermainwindow.cpp:25-27,849-850）。

库接入者

库接入的最小生命周期是主线程 initialize() → 发起/等待请求 → 主线程 unInitialize()。不要从 worker 线程初始化全局 Manager；不要在请求仍活动时假设反初始化会无限等待，详见第 04 篇。

3. 构建产物与动态库查找

Windows

CMake 常见布局：

主库和 OpenSSL DLL 由后构建命令复制到目标目录（cmake/utilities.cmake:23-59）。Qt Widgets/Gui/Network/Xml 等 DLL 不会由普通 CMake build 自动收集；需要 Qt bin 在 PATH，或使用 windeployqt。

本地 PowerShell 启动示例，本次未执行：

DLL 缺失时先核对：exe 架构、Qt 编译器/版本、Debug/Release CRT、OpenSSL 主版本、主库是否同目录、Qt platforms/qwindows.dll 是否可找到。不要把不同 Qt 小版本或 Debug/Release DLL 混用。

Linux/macOS

可执行文件在 build/<Config>/。共享库搜索依赖系统 Qt、LD_LIBRARY_PATH（Linux）、DYLD_LIBRARY_PATH/install name（macOS）或部署工具。脚本最后也明确提示 Linux 运行前确保 Qt 库可找到（scripts/build_linux.sh:243-256）。本次未验证具体安装名称和 rpath。

4. 应用数据与持久化格式

4.1 QtRequester

目录：QStandardPaths::writableLocation(QStandardPaths::AppDataLocation) + "/requests"（networkrequesttool.cpp:2123-2133）。实际系统路径受 QApplication 组织/应用名影响，运行时应通过 Qt API查询，不要硬编码。

主要文件：

文件 内容 安全/行为注意
environments.json 命名环境、变量、active 环境 变量可能含 token/URL；明文
请求 JSON method、url、body、bodyType、rawType、timestamp、params、headers、auth 保存 Basic 密码、Bearer token、API Key、OAuth2 client secret/refresh token 等明文
collection.json 文件夹/请求树及请求 JSON 同样可能携带认证字段
秒级时间戳请求 JSON method、url、body、bodyType、rawType、params、headers、auth、timestamp 点击 Save 时；同秒可能覆盖
内存历史 RequestHistory 仅保存在进程内，上限 100 条 点击 Save 时追加；重启不恢复，也不落盘为历史文件
Postman JSON v2.1 部分字段导入/导出 不支持完整规范，不要当无损交换格式

saveToDisk() 明确把认证字段写入 JSON（networkrequesttool.cpp:2341-2415）。因此：

  • 不要把这些文件提交到 Git、上传日志或作为无敏感数据附件分享；
  • 文件权限、磁盘加密和备份保留周期由操作系统/用户负责，代码未提供加密；
  • 测试/排障时优先使用临时应用数据目录或测试注入，避免读取真实凭据；
  • 泄露后应轮换对应 token/密码，而不是只删除本地 JSON。

环境切换只改内存 active；管理对话框接受后的 active 保存存在已确认断线，详见第 09/10 篇。

4.2 QtDownloader

设置存储：QSettings("QtDownloader","Downloader")（downloadmanager.cpp:10-17）。Windows 通常进入注册表，Unix 通常进入用户配置文件；具体位置由 Qt 平台实现决定。

保存键（downloadmanager.cpp:331-407）：

规则：

  • setMaxThreads() 限制 1–64；并发任务限制 1–20（downloadmanager.cpp:64-83）。
  • 每次保存任务先清空 Tasks 组再重写，不是事务数据库。
  • Completed/Error 任务不恢复；其他状态统一重置 Waiting。
  • savePath 虽保存，实际下载仍使用全局 m_downloadDir。
  • 恢复发生在主窗口 setupConnections() 前，taskAdded 信号丢失，持久任务可能不进 UI Model，详见第 11 篇。
  • “继续”不是断点续传；已保存 downloadedBytes 不代表能接着写。

5. IDE 与调试入口

.vscode/launch.json:6-45 提供 request tool/downloader 两个 cppvsdbg 配置，使用 CMake launch target，并把 ${env:QT_DIR}/bin 追加到 PATH。downloader 还启用 natvis 和引擎日志。docs/vscode-setup-guide.md 与 .vscode/README.md 提供环境准备说明。

注意事项：

  • 两份文档部分命令按 CMD 编写，在 PowerShell 中应使用 $env:QT_DIR=...，不能直接照搬 set QT_DIR=...。
  • .vscode/README.md 对 Qt6 写“需要适当调整”，不能视为 Qt6 已验证。
  • 启动目标由 CMake Tools 当前选择决定；调试 Downloader 时需确认 launch target 不是 QtRequester。
  • 修改 QT_DIR 后重载窗口；Qt/CRT/DLL 问题先在干净 shell 复现，再判断 IDE 配置。
  • 调试日志可能包含 URL、Header、Cookie 或响应体，分享前必须脱敏。

6. 安装与 Windows 打包

6.1 CMake install

安装内容（source/CMakeLists.txt:112-154）：

  • 共享库到 bin/lib；
  • include/ 下全部公共 .h 到 include；
  • QtNetworkRequestTargets.cmake、Config、Version 到 lib/cmake/QtNetworkRequest。

适合 C++ 开发者消费，不等于 GUI 发布包。独立工程必须自行查找 Qt Core/Network，并确保运行时 DLL 可解析；Config 当前不自动 find_dependency(Qt...)。

6.2 pack.bat 流程

scripts/pack.bat:14-115：

  1. 删除并重建仓库 install/、installer/；
  2. 要求 build/Release 存在，复制全部产物到 install；
  3. 校验 QtRequester.exe、QtDownloader.exe、QNetworkRequest.dll；
  4. 对两个 exe 执行 windeployqt --release ...；
  5. 根据 install 中是否存在旧 OpenSSL DLL 选择 1.0.2/1.1.1；
  6. 检查 WiX，构建两个 MSI。

build_and_pack.bat:5-20 会先调用 build_win.bat，后者清理 build/install。执行前必须确认没有需要保留的未提交或本地生成文件。

6.3 已确认发布阻塞

阻塞 证据 后果
WXS 使用旧 QtRequester exe 名 pack.bat:81-95 校验新名；scripts/Package.wxs:30-32 Source 为 install\QtNetworkRequestTool.exe WiX 找不到源文件，MSI 构建失败
QtRequester 快捷方式使用第三个旧名 scripts/Package.wxs:199-204 Target 为 NetworkRequestTool.exe 即使修复 Source，快捷方式仍会指向不存在的程序
WXS 使用旧 QtDownloader exe 名 scripts/Package_QtDownloader.wxs:30-32 Source 为 install\QtNetworkDownloader.exe 同上
固定 OpenSSL 1.1.1 文件名 pack.bat:117-131 不匹配其他 OpenSSL/Qt6 部署
MSI 版本固定 1.0.0 pack.bat:144-175、WXS Version="1.0.0.0" 与库 2.2.1/Changelog 2.3.0 分裂
WXS 显式列举 Qt5 DLL 两个 WXS ProductComponents Qt6 产物名不同，当前清单不能直接用于 Qt6
无干净机验收 仓库无对应测试证据 windeployqt 成功不代表 MSI 安装后能启动

因此当前状态应表述为“发布脚本与清单存在，但未闭环、不能据此宣称可发布”，而不是“MSI 已可用”。

7. 配置优先级速查

示例请求配置可概括为：

需要避免的误解：

  • QtRequester 的 URL 内联 Query 会被 QUrl::RemoveQuery 丢弃，只发送 Params 表（第 10 篇）。
  • GUI 设置不是所有请求类都走同一准备路径；NetworkUploadRequest 当前不调用完整 prepareRequest/auth/bodyContentType 链（第 06 篇）。
  • 代理默认优先级与逐请求覆盖、NAM 获取时恢复默认代理的细节见第 08 篇。
  • Qt 自动管理的 Header 不应手工重复设置；项目已有统一策略，修改前先读相关主题。
  • 下载器的 threadCount 是每任务 Range 通道上限，MaxConcurrentDownloads 是任务级并发；总连接数不等于二者简单相加的固定值。

8. 运行检查清单

构建后建议按以下顺序排查，本次未执行：

  1. 版本/架构：记录 Qt、编译器、CMake、OpenSSL、Config、exe 架构。
  2. 启动：在干净环境启动 exe；区分主库/Qt/OpenSSL/plugin 哪一类 DLL 缺失。
  3. 生命周期：确认主线程 initialize，退出时无长时间活动请求。
  4. 网络：先用可控本地 HTTP 服务验证，再测试 HTTPS；记录系统代理与应用代理。
  5. 文件：使用临时目录验证覆盖、取消、错误和服务端文件名；检查残留文件。
  6. 配置：备份或隔离 AppData/QSettings，避免真实凭据和主题被改动。
  7. GUI：验证主题、窗口恢复、任务/环境/集合持久化及重启行为。
  8. 发布：修复 WXS 后 clean build → pack → 干净虚拟机安装 → 启动/请求/下载/卸载。
