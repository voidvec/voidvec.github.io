多线程分片下载的状态机

AR##-进阶
发表于2026-11-25|更新于2026-11-25|框架库Qt框架
|浏览量:
项目/qt-network-request/设计与架构
qt-network-request架构设计进阶

1. 定位与结论

本文解释 NetworkMTDownloadRequest 如何探测服务器、划分区间、并发接收、写映射文件和提交最终文件。核心结论：

  • “MT”是同一个工作线程、同一个 NAM 上的多个异步 HTTP Range 通道，不是 N 个 OS 下载线程。
  • 状态机为 Probe(HEAD) → 可选 RangeProbe(GET bytes=0-0) → MultiDownload。
  • 服务器不声明 Accept-Ranges: bytes 或探测不是 206 时回退单通道，但仍走 MT 的临时文件/映射流程。
  • 探测只检查 206，不验证 Content-Range；分片完成只检查 Qt 无错误和 HTTP 2xx，不要求 206，也不比较预期长度或实际写入长度。
  • 分片直接随机写入同一个预扩展文件，不存在“分别下载后再拼接”的独立阶段。
  • 当前没有 ETag、哈希、长度一致性、断点续传或分片重试契约；进度 100% 和最终 rename 不能证明内容正确。

2. 触发条件与并发模型

Registry 在以下情况选择 MT：

  • 显式 RequestType::MTDownload。
  • RequestType::Download 且 threadCount>1。
  • RequestType::Download 且 threadCount=0 自动模式。

threadCount=0 时读取 QThread::idealThreadCount()；Range 可用时最少调整为 2，Range 不可用时固定 1。它不受 NetworkRequestManager::setMaxThreadCount() 的直接“每任务线程数”语义控制。

每个 Downloader：

  • 是普通 QObject，不是 QRunnable。
  • 与所属 NetworkMTDownloadRequest 在同一工作线程运行。
  • 使用同一个线程亲和 NAM 发起异步 GET。
  • Qt 事件循环交错推进多个 Reply。

4. ProbeState：HEAD 探测

doProbeRequest()：

  • 获取 NAM、应用 proxy。
  • 对 URL 发 HEAD，设置 transfer timeout 和 TLS。
  • 没有在该阶段附加用户 Header、认证 Header、queryParams 或 Cookie 列表；不能把普通请求的完整配置语义直接套到 HEAD。

handleProbeFinished()：

  1. 通过 evaluateOutcome() 判断 HTTP(S) 成功。
  2. 301/302 时解析目标并在计数内重新 HEAD。
  3. 其他失败尝试 tryRetry()，默认关闭重试。
  4. 读取 Content-Length 为 m_fileSize。
  5. 读取 Accept-Ranges，仅做不区分大小写的 contains("bytes")。
  6. 保存响应 Header，并附加 X-Final-Url。
  7. 删除 HEAD Reply，进入 RangeProbe 或直接 MultiDownload。

边界：

  • 没有 Content-Length 或长度≤0 时最终返回 ContentLengthMissing。
  • HEAD 失败与文件大小获取失败混在一条错误路径，未提供更细的服务器原因。
  • HEAD 成功不代表后续 GET 支持 Range。
  • HEAD 本身没有 Body，不应期待从它获得文件内容。

同时：

  • Qt ≥5.13 时禁用 HTTP/2。
  • 禁用 HTTP pipelining。
  • 应用 TLS 配置。

handleRangeProbeFinished() 只做：

  • 206 → 保留请求的通道数。
  • 非 206 → 将 downloadConfig.threadCount 改为 1。
  • 不检查 reply->error()、Content-Range、Body 长度或 Body 首字节。
  • 不读取/清理探测 Body，只 deleteLater()。

因此以下情况都没有被显式验证：

  • 206 但 Content-Range 缺失/错误。
  • 206 但范围不是 bytes 0-0/size。
  • 206 但 Body 长度不是 1。
  • 非 206 错误响应被当作“不支持 Range”而不是协议错误。

  • 通道数大于文件字节数时，可能出现重复或零长度区间；当前没有限制通道数≤文件大小。
  • 大文件乘法与进度累加使用 qint64，仍需极端大文件测试。

7. Downloader：Range 请求与写入

每个 Downloader 发送：

实现细节：

  • 使用小写 bytes=，符合 Range 单位大小写要求。
  • 禁用 HTTP/2 与 pipelining，降低 CDN 丢弃 Range 的风险。
  • 应用请求级/全局 TLS 解析。
  • readyRead 将 Body 限制在剩余区间长度内。
  • 写入位置为 startPoint + m_bytesWritten。
  • 调用 MemoryMappedFile::write() 随机写入同一映射。

7.1 写入错误未进入完成判定

Downloader::onReadyRead()：

  • 映射写返回≤0 时记录 m_errorMessage，但继续等待完成。
  • 短写只增加实际写入字节，不主动失败。
  • 超出预期区间的数据只记录一次 overflow 日志，不主动失败。
  • 映射未打开也只记录错误。

Downloader::onFinished()：

  • success = (Qt error == NoError)。
  • HTTP(S) 再要求 2xx。
  • 不要求 206。
  • **不比较 Content-Range**。
  • **不比较 end-start+1 与 m_bytesWritten**。
  • 不把 m_errorMessage 或 flush 失败转成失败。
  • 成功后调用 flush()，但忽略返回值。

因此服务器在探测后忽略 Range 返回 200 时，每个通道只写自己区间长度的前缀，未覆盖区域可能保持预扩展零值，最终仍可能成功。

8. 重定向与重试

8.1 HEAD

  • 支持 301/302，受 maxRedirectionCount 限制。
  • 其他失败可走公共 tryRetry()。

8.2 分片

  • 分片 Downloader 自己处理 301/302，沿用原 Range 重启。
  • 没有分片级指数退避或 maxRetryCount。
  • 首个分片失败会触发整体 abort，其他分片被清理。
  • 不单独重试失败区间。

这与普通请求“显式开启重试”不同，不能认为 retryOnFailed=true 会给每个 Range 通道同样保护。

9. 完成、flush 与 rename

onSubPartFinished()：

  • 用 m_finishedPartIds 去重。
  • 成功计数加一；首个失败立即 abort。
  • successCount == threadCount 且无失败时：
    1. 计算耗时/速度。
    2. 关闭映射。
    3. renameTempFileToFinal()。
    4. 设置 m_bytesReceived=m_fileSize。
    5. 返回成功 Body（耗时/速度文本）和 HEAD 保存的 Header。
  • 失败返回错误，abort 通常已删除临时文件。

renameTempFileToFinal()：

  • 临时文件不存在则失败。
  • 最终文件存在且不允许覆盖则失败。
  • 允许覆盖时先删除最终文件，再 rename。
  • rename 成功才清空 m_tempFilePath。

重要限制：

  • m_bytesReceived=m_fileSize 是设计值，不是逐字节核对值。
  • flush() 失败被忽略。
  • rename 失败时临时文件可能仍存在，主要依赖后续析构/abort 清理。
  • 先删除最终文件再 rename 不是原子替换；两步之间失败可能造成旧文件丢失、新文件未就位。
  • 下载完成后没有重新打开文件验证大小或内容。

10. 进度与速度

  • 每个 Downloader 通过 downloadProgress 上报当前区间已接收字节。
  • 父请求按 part 累加，除以 HEAD 得到的总大小。
  • ProgressThrottle 降低单个通道事件频率。
  • 最终速度 = 文件大小 / 总耗时。

边界：

  • 进度基于网络报告，不是实际写入字节。
  • 服务器忽略 Range 时可能超过 100% 或错误汇总。
  • 通道数极多、文件很小、零长度区间时进度分母/重复计数需验证。
  • 总耗时包含映射、flush、rename，速度不是纯网络吞吐。

11. 取消与文件状态

NetworkMTDownloadRequest::abort()：

  1. 调用基类 abort，停止主 Reply。
  2. clearDownloaders() 停止分片 Reply。
  3. 关闭并释放映射。
  4. 删除 UUID 临时文件。
  5. 清空进度。

因此正常 abort 路径通常不留下临时文件，也不修改已存在的最终文件。但：

  • 已经 rename 成功后取消不会回滚最终文件。
  • rename 失败、进程崩溃、强制终止不保证清理。
  • 早期返回若未 abort，可能依赖析构清理。
  • 取消终态是否投递给调用方取决于 Manager 停止 API。

12. 协议与能力边界

  • MT 下载依赖 HTTP HEAD/GET/Range/206；FTP 不能据此宣称支持分片。
  • 单通道回退仍发 Range: bytes=0-<size-1>，某些严格服务器可能拒绝带 Range 的请求；未验证。
  • 不支持服务端不提供 Content-Length 的 chunked 大文件。
  • 不支持验证码、签名 URL 刷新、临时访问链接过期后的重新授权。
  • 没有用户 Header/认证 Header/queryParams 的完整探测和分片传递；签名 Query 若已在 URL 中会保留，独立 queryParams 不能假定追加。
  • Cookie 依赖 NAM Jar；请求级 m_context->cookies 没有在该路径逐个插入。
