简介

本文件系统性说明 Fulla 的授权安全能力，重点覆盖：

  • RBAC（基于角色的访问控制）模型、角色与权限定义、继承与分配机制
  • 权限验证机制：资源/操作 scope、角色权限并集与组织上下文门
  • OAuth2/OIDC Scope 细粒度权限控制与令牌/introspection 结果校验
  • API 端点保护：过滤器规则、scope 决策与管理 scope 门；不把设计建议当作已实现的风控引擎
  • 权限模型设计指南与最佳实践（最小权限原则、职责分离）

项目结构

Fulla 将授权相关能力分布在以下层次：

  • 数据层：RBAC 与 Scope 的持久化迁移脚本
  • 框架层：Drogon 过滤器（AuthorizationFilter）实现请求级鉴权拦截
  • 服务装配：身份装配与控制器注册，统一挂载安全策略
  • 文档与契约：OpenAPI 描述端点与安全方案
  • 集成测试：针对 Scope 校验等关键路径的行为验证

核心组件

  • RBAC 数据模型与默认初始化：通过迁移脚本创建角色、权限及关联表，并注入默认角色与权限
  • 请求级鉴权过滤器：在 Drogon 管道中拦截请求，解析令牌、加载主体与角色/权限，执行匹配与放行/拒绝决策
  • OAuth2/OIDC Scope 支持：通过数据库存储 Scope 集合，并在客户端凭证流程中进行范围校验
  • OpenAPI 安全方案：以标准方式声明端点所需的认证与范围

RBAC 数据模型与默认初始化

  • 角色与权限：roles、permissions 表提供基础实体
  • 关联关系：user_roles（用户-角色）、role_permissions（角色-权限）建立多对多映射
  • 索引优化：对用户与角色维度建立索引，提升查询效率
  • 默认数据：内置 admin/user 角色与若干权限，并将全部权限授予 admin，user 仅授予基础读取权限

RBAC 权限级执行（v1.6.0，ADR-0014）

增量补篇：对应本 wiki 快照之后 v1.6.0 落地的 RBAC 权限执行，总览见 [[versioning-and-release-guide-zh]]。

  • 背景：V005 的 RBAC 表（roles/permissions/user_roles/role_permissions）长期”有 schema、无执行”——没有任何业务代码读 role_permissions 做授权决策。实际把守管理操作的是两道并行链：oauth2_scopes.requires_admin_role 列（启动时注入 ScopeDecisionEngine 的谓词）与 IdentityService 硬编码的管理 scope 字面集；两道都要求字面 admin 角色，”只读用户的帮助台角色”这类委托管理员完全无法表达（ADR-0014）。
  • 语义：permissions 行重新定义为**”角色持有某资源 scope 的权利”**——权限名即资源 scope 名（users:read、clients:write、audit:read 等，V023 的 resource-scope 词汇表），不发明新权限文法；细粒度授权面保持 OAuth2 scope 模型（scope 目录 + ResourceScopeRegistry (path,method)→scope + 同意）。
  • 集成进三道门（Erratum 2）：P1-8 对弈性复核确认真实拓扑是三道门——上述两道 scope 链，加上 HTTP 层 AuthorizationFilter::checkAccess（rbac_rules 正则 → 字面角色，DEFAULT DENY；不打通它，委托管理员在任何 scope 逻辑运行前就被 403）。落地形态：
    • 分类与判定解耦：requires_admin_role 列仍是管理类目来源（废弃，读至 v2.0）；用户能否通过改为权限判定（角色的权限并集覆盖该 scope，或持有 admin 超级 scope）。
    • rbac_rules 条目接受 {"permissions": [...]}，最具体优先匹配；catch-all 与 DEFAULT DENY 基线不动。
    • 两步登录路径的 scope 现在经同一引擎分层过滤（此前签发未过滤的授权码）。
  • 兼容种子：迁移为 admin 角色授予 scope 目录中的全部资源 scope（行为前后逐字节一致）；V043 播种权限目录（九个 V023 名称 + admin），四个 V005 旧权限名原地退役（UPDATE，不 DELETE）。
  • 解锁能力：自定义角色可授予子集（如 helpdesk = 仅 users:read），管理控制台角色页新增角色→scope 集分配 UI；验收标准为”仅有 users:read 的新帮助台角色可以列用户且仅此而已，admin 角色行为与之前完全一致”。

请求级鉴权过滤器（AuthorizationFilter）

  • 拦截位置：Drogon 过滤器链，优先于控制器执行
  • 主要职责：
    • 解析 Bearer Access Token，提取主体信息（不以 JSESSIONID 作为 API 主认证会话）
    • 根据主体加载角色与权限集合（可结合缓存）
    • 依据 URL/方法匹配 rbac_rules；最具体规则可要求角色或 permissions 资源-scope 集（v1.6.0）
    • 决策放行或返回 401/403
  • 与配置的关系：可通过配置文件定义 URL 模式到所需角色的映射，采用 OR 逻辑匹配；v1.6.0（ADR-0014）起条目可携带 {"permissions":[...]}（permission = 角色的资源-scope 集），最具体优先匹配，catch-all 与 DEFAULT DENY 基线不变——详见上文「RBAC 权限级执行」小节。

OAuth2/OIDC Scope 细粒度权限控制

  • Scope 存储：通过迁移脚本维护 Scope 集合，供客户端申请与服务器校验
  • 客户端凭证流程：在服务端颁发令牌时，校验请求 Scope 是否合法，并在令牌中携带必要声明
  • 集成测试：针对客户端凭证流程的 Scope 校验行为进行回归验证
  • （v1.5.0）协议面的 scope 语义收紧——authorize 端点 PKCE 仅 S256、userinfo 声明按 profile/email scope 门控、token subject 统一为 UUID public_sub——已由 [[oauth2-oidc-security]] 与 [[versioning-and-release-guide-zh]] 覆盖，此处不展开。

令牌校验、内省与权限判定

  • API 主路径只从 Bearer header 提取随机不透明 access token，由 TokenService 查询存储并检查记录存在、revoked 与 expiry，再从令牌记录或主体加载 scope；不是 JWT 验签路径。普通 TokenService 校验不检查 nbf，而 Redis 缓存装饰层的读取/回填与 introspection 仓库会检查 nbf。
  • 权限事实以服务端角色与资源-scope 关系为准，不必把完整角色集塞进令牌；v1.6.0 permission 即角色可持有的资源 scope。
  • 未发布 introspection 仅对 active 返回 metadata + Cache-Control: no-store，并叠加 owner 状态：Active/Unmanaged 放行，Suspended/Unavailable 拒绝；owner 查询错误或超时不缓存。
  • introspection 的 org_id 是令牌事实，不是实时组织成员资格；active 也不代表族撤销已全局即时收敛。资源服务器若需实时租户权限，应另查权威状态。

API 端点的权限保护机制

  • 中间件过滤：通过 AuthorizationFilter 统一拦截，实现“先鉴权后路由”
  • 注解/契约驱动：OpenAPI 与控制器描述安全要求；实际放行仍需 AuthorizationFilter、scope 决策与管理 scope 门共同执行，不能把声明当成自动校验。
  • 开放接口：公开端点（如健康检查、发现文档）可配置为免鉴权或通过轻量校验；白名单必须显式，未匹配规则保持拒绝。
  • 契约声明：OpenAPI 中声明各端点的安全方案（Bearer/JWT/Scope），便于生成客户端与网关策略

上下文感知授权

  • 已实现上下文：组织成员资格/客户端归属或组织同意、组织 require_mfa、主体角色与资源-scope 并集。
  • 设计方向而非现状：设备指纹、IP/地理位置、时间窗口、风险评分及动态收紧权限；不能据此宣称 Fulla 已有完整风险自适应授权引擎。
  • 审计记录：关键决策与拒绝事件可进入审计链路；审计能力不替代实时授权校验。
  • 组织级管理员同意（v1.4.0）：组织 owner/管理员可代表组织授予同意——成员对已覆盖 scope 跳过个人同意提示，仅改变提示行为，绝不放大 scope；无管理权的成员提交同意请求，由管理者在门户批准/拒绝；撤销仅影响未来授权（按租户裁决，在途令牌不动）。组织级协议边界（org_id 门、org_ctx 声明）见 [[security-architecture-zh]]。

性能考虑

  • 角色/权限缓存：可用于减少重复查询，但需明确失效策略；未发布令牌缓存有 org 绑定、5 秒本地截止且无 stale fallback，不能据此宣称角色变更全局即时生效。
  • 索引优化：确保 user_roles、role_permissions 等高频查询字段有合适索引
  • 令牌体积控制：仅在令牌中包含必要声明，降低解析与传输开销
  • 批量加载：按主体一次性加载角色与权限，避免 N+1 查询

故障排查指南

  • 401/403 频繁出现：
    • 检查令牌是否有效、是否包含必要声明
    • 核对 rbac_rules 与控制器注解是否一致
    • 确认用户是否已正确分配角色/权限
  • Scope 校验失败：
    • 检查客户端申请的 scope 是否在数据库中登记
    • 核对服务端颁发令牌时对 scope 的校验逻辑
  • 性能问题：
    • 观察过滤器耗时，定位是否为数据库查询瓶颈
    • 增加缓存或优化 SQL

结论

Fulla 通过 RBAC 数据模型、请求级过滤器与 OAuth2/OIDc Scope 机制，构建了端到端的授权体系。借助 OpenAPI 契约与启动装配，系统实现了“声明式安全 + 运行时校验”的统一治理。遵循最小权限与职责分离原则，可有效降低越权风险并提升可维护性。

附录

权限模型设计指南与最佳实践

  • 最小权限原则：仅授予完成工作所需的最小权限集合，定期回收冗余权限
  • 职责分离：将管理员、普通用户、只读角色等职责清晰划分，避免权限叠加
  • 角色继承：通过角色组合与权限聚合实现继承，避免硬编码分支
  • 资源/操作/上下文三维控制：以资源维度限定对象，以操作维度限定动作，以上下文维度限制场景
  • 审计与可观测性：记录授权决策与拒绝原因，支撑事后追溯与合规审计
  • 令牌治理：短生命周期令牌 + 刷新机制；谨慎声明敏感信息
  • 配置即策略：将 URL 到角色的映射集中管理，便于变更与审查
