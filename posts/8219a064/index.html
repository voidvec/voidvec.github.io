公共 API 与数据契约

发表于2026-11-25|更新于2026-11-25|框架库Qt框架
|浏览量:
项目/qt-network-request/设计与架构
qt-network-request接口与协议进阶

1. 定位与结论

本文面向库调用者、示例维护者和接口评审者，说明“调用方传入什么、库返回什么、哪些默认行为容易误判”。核心结论：

  • 公共契约由 include/ 头文件表达，实现位于 source/；构建者应优先链接 QNetworkRequest，不要直接依赖私有类。
  • RequestContext 是完整请求配置载体，RequestContextBuilder 是推荐入口，但 Builder 只能消费一次。
  • 当前结果是结构化的 ResponseResult + ErrorInfo，README 中部分扁平结果字段已过期。
  • postRequest 的返回值表示请求已受理，不表示网络成功；同步的 sendRequest 仍不提供 HTTP 业务成功返回值。
  • 公共 API 并非所有方法都可无约束跨线程调用；线程亲和、初始化和停止语义必须与第 04 篇一起阅读。

2. 模块边界与公共文件

公共目录包含 16 个头文件，可分成五组：

组 文件 作用
请求输入 include/requestcontext.h 请求类型、URL、Header、Body、认证、上传/下载、行为配置及 Builder
请求标识 include/taskdata.h TaskData、BatchRequestPtrTasks、RequestType
异步句柄 include/networkreply.h 单请求/批次的完成、进度、错误与停止信号
结果与错误 include/responseresult.h、include/networkerror.h 成功判定、HTTP 状态、响应、性能、结构化错误
基础设施入口 include/networkrequestmanager.h、include/networkrequestglobal.h 生命周期、调度、全局配置、取消、导出宏
认证与网络策略 include/authconfig.h、include/sslconfig.h、include/proxyconfig.h 认证注入、TLS 策略、代理配置
环境与集合 include/environment.h、include/environmentstore.h、include/oauth2tokencache.h、include/collectionmodel.h、include/postmanconverter.h 变量替换、命名环境、Token 缓存、集合树、Postman 映射

AGENTS.md 的“公共头 9 个”与其后目录清单及实际文件不一致；公共 API 盘点应以 include/ 实际内容为准。

3. 请求输入：RequestContext

3.1 请求类型与协议边界

RequestType 定义于 include/taskdata.h:50-86：

  • 通用方法：Get、Post、Put、Delete、Head、Patch、Options。
  • 特殊传输：Download、MTDownload、Upload。
  • 未指定时为 Unknown；注册表找不到处理器时产生 UnsupportedRequestType。

头文件注释将 MTDownload 及 POST/DELETE/HEAD/PATCH/OPTIONS 限定为 HTTP(S)。实现中，普通请求明确拒绝 FTP 的 POST/DELETE/HEAD；多线程下载实现依赖 HTTP HEAD、Range 和 206，不能据此宣称支持 FTP 分片。具体传输边界见第 06、07 篇。

3.2 关键默认值

依据 include/requestcontext.h:65-145：

字段 默认值 解释
behavior.showProgress false 不订阅下载进度；调用方仍需了解具体请求类的连接条件
behavior.retryOnFailed false 默认不重试
behavior.maxRetryCount 3 仅在显式开启重试后使用
behavior.retryDelayMs 1000 重试基础间隔
behavior.maxRedirectionCount 3 仅处理当前实现支持的重定向
behavior.transferTimeout 30000 单次传输阶段超时，不是总耗时
behavior.idleTimeoutMs 0 默认关闭 idle 超时
behavior.totalTimeoutMs 0 默认不限制总耗时
behavior.priority 0 线程池队列优先级
download.overwriteFile false 单线程与 MT 的同名处理并不相同
download.threadCount 0 自动检测 CPU；实际通道数还会受 Range 探测影响
type Unknown 必须显式选择请求类型
bodyType None 影响文本/Body 类型与 Content-Type
headers、body、url 空 不做完整业务校验
认证、代理、下载、上传配置指针 空 各功能路径按需判空或使用默认行为

这些默认值说明库提供网络执行能力，不提供完整 API 契约校验。缺少协议、Header、Body、目标路径等业务条件时，调用方仍需自行校验。

4. Builder：推荐入口与消费语义

推荐形式：

需要特别注意：

  1. build() 返回 std::unique_ptr<RequestContext>，并移动 Builder 内部上下文；同一 Builder 不能再次构建，见 include/requestcontext.h:393-401。
  2. .timeout(ms) 设置的是 totalTimeoutMs，不是 transferTimeout，见 include/requestcontext.h:324-327。
  3. .retry(...) 同时开启重试，不只是设置最大次数，见 include/requestcontext.h:339-344。
  4. setter 基本不做范围校验；线程数、重试次数等可能在赋值时窄化为 quint16。不要依赖“极大值会被安全拒绝”。
  5. Builder 只负责组装数据，不创建网络请求，也不保证 URL 可连接或认证配置完整。

5. 输出：ResponseResult 与 ErrorInfo

当前定义见 include/responseresult.h:43-84：

使用规则：

  • 先检查 error.category/code/message，再结合 statusCode 解释业务结果；isSuccess() 仅表示结构化错误为空。
  • statusCode=0 可能代表本地失败、取消或未获得 HTTP 状态，不能一律视为 HTTP 200。
  • body 不是所有请求类型都填充：下载类主要写文件；失败响应体当前也可能为空。
  • performance 是累计/估算数据，不应替代服务端指标或精确计费数据。
  • task.id/batchId/sessionId/startTime/endTime 用于关联异步结果与取消操作；请求 ID 由 Manager 统一生成。
  • userContext 是调用方透传上下文，库不解释其业务含义。

ErrorInfo 将错误分为配置、网络、协议、HTTP、认证、文件 I/O、超时、取消等类别，并提供稳定 ErrorCode。完整映射及重试关系见第 05 篇。README 中旧的 success/cancelled/errorMessage 扁平模型不应再作为编译依据。

6. 异步句柄：NetworkReply

NetworkReply 不是 QNetworkReply，而是库对外的任务结果句柄：

  • requestFinished(QSharedPointer<ResponseResult>)：单个子请求完成。
  • downloadProgress / uploadProgress：进度变化。
  • error(QString)：供 UI 展示错误消息。
  • batchRequestFinished(quint64, bool)：批次结束信号由 Manager 发出，不是每个 NetworkReply 独立产生。

生命周期事实：

  • Manager 内部持有 shared_ptr<NetworkReply>；外部也持有 shared_ptr，因此 Manager 移除映射不等于外部句柄立即失效。
  • 头文件中“自动销毁”的简化注释不能理解为“完成即释放”。
  • 对 UI 而言，应保留需要的句柄，断开连接或退出页面时释放自己的引用，避免向已销毁接收者投递信号。

7. Manager API 契约

7.1 初始化

标准顺序：

initialize() / unInitialize() 应在主线程调用。当前实现具有顺序调用上的幂等保护，但没有用运行时断言强制主线程约束；反初始化采用等待与强制清理结合，不保证所有长任务自然结束。详见第 04、14 篇。

7.2 异步入口

  • postRequest(unique_ptr<RequestContext>)：提交单请求，返回任务句柄；未初始化、非法 URL 等受理前失败可返回空指针。
  • postBatchRequest(BatchRequestPtrTasks&&, batchId)：提交同批任务，共用一个 NetworkReply，每个子结果仍通过 requestFinished 返回。
  • 成功受理只意味着进入执行/排队流程；真正的终态来自结果信号。

7.3 同步入口

sendRequest(context, callback, blockUserInteraction=true) 会嵌套事件循环等待结果，并在返回前执行 callback。其 bool 只表示是否受理/获得空闲线程，不表示 HTTP 成功。非阻塞选项并不把请求变成普通异步 API，调用方必须保证 callback 所需对象存活。

7.4 配置与取消

  • setGlobalProxy/globalProxy：全局代理；请求级配置可覆盖。
  • setGlobalSslConfig/globalSslConfig：全局 TLS；按值返回并带锁。
  • setCookieStoragePath/cookieJar：Cookie 持久化路径与共享 Jar。
  • setMaxThreadCount：线程池最大并发；下载 threadCount 是另一概念。
  • stopRequest/stopBatchRequests/stopSessionRequest/stopAllRequest：语义并不相同，是否发送 Cancelled 终态需按第 04 篇矩阵处理。

8. 数据契约之间的关系

三个容易混淆的标识：

  • 请求 ID：一个实际执行单元。
  • 批次 ID：一次批量提交的关联标识。
  • 会话 ID：调用方建立的取消分组，不自动形成持久会话。

9. 调用注意事项

  1. 不要直接构造私有 NetworkRequest 子类或访问 Manager d_ptr。
  2. 不要把请求级 download.threadCount 与 setMaxThreadCount 混为一谈：前者控制单个 MT 下载通道，后者限制全局工作线程。
  3. 不要假设所有请求都返回内存 Body；下载、FTP、失败响应和大文件路径需要分别处理。
  4. 不要假设 Builder 或 Result 会替你验证 API 业务约束。
  5. 不要从 UI 线程直接删除工作线程中的 NAM、Reply 或请求对象。
  6. 不要在未检查初始化状态和空句柄的情况下解引用返回值。
  7. 不要依据 README 的旧结果模型编写迁移代码；以当前头文件为准。
