请求生命周期与并发模型

发表于2026-11-25|更新于2026-11-25|框架库Qt框架
|浏览量:
项目/qt-network-request/设计与架构
qt-network-request架构设计进阶

1. 定位与结论

本文解释一次请求从提交到返回结果的全过程，重点回答：代码在哪个线程执行、如何等待异步 Qt 网络、如何取消、反初始化会发生什么。核心结论：

  • Manager 在主线程管理映射、事件和结果转发；实际请求由 QThreadPool 中的 Runnable 执行。
  • 每个工作线程从池中取得线程亲和的 QNetworkAccessManager，通过局部 QEventLoop 等待异步网络，不阻塞调用线程。
  • “一个请求一个线程”描述的是工作执行槽，不是每次网络 I/O 都独占 OS 线程，更不是 MT 下载的 N 个 OS 线程。
  • 取消 API 的终态语义不统一；stopSessionRequest / stopAllRequest 不能默认理解为“保证收到 Cancelled 回调”。
  • 公共头中的“Thread-safe”是总体意图，不能替代逐 API 的线程亲和和锁分析。

2. 运行角色

角色 线程/所有权 职责
NetworkRequestManager 主线程 QObject 初始化、ID、映射、停止、进度、结果转发
NetworkRequestRunnable 由 QThreadPool 调度 消费 Context、创建请求、运行事件循环、发送一次终态
NetworkRequest 子类 Runnable 所在工作线程 创建 NAM 请求、处理 Qt 信号、重试/重定向、生成 Result
QNetworkAccessManagerPool 按线程保存 NAM 提供线程亲和 NAM，代理/Cookie/TLS 附着
QNetworkReply 工作线程 NAM 所有 异步网络状态与数据
对外 NetworkReply shared_ptr 主线程结果句柄，向调用方发信号

3. 初始化与反初始化

3.1 初始化

  • initialize() 在主线程创建 Manager、线程池和 NAM 池，并恢复持久 Cookie。
  • 顺序重复调用具有幂等保护；isInitialized() 反映初始化原子状态。
  • 头文件要求主线程调用，但当前没有运行时主线程断言。
  • 调用方应在应用启动阶段完成初始化，而不是在 worker 中首次请求时惰性初始化。

3.2 反初始化

实现步骤概括为：

  1. 标记正在反初始化并设置全局停止标志。
  2. 停止请求、清理映射。
  3. 等待约 1 秒。
  4. 通过同线程清理 QRunnable 销毁各工作线程的 NAM。
  5. 再等待约 2 秒。
  6. 对残余 NAM 执行 deleteLater/detach 等清理，避免跨线程直接析构。

这不是事务式优雅关闭：固定等待不能保证任意长请求、锁竞争或挂死网络都已完成。应用退出前应显式停止任务、断开 UI 连接，并给短请求留出完成时间。

4. 异步单请求主路径

关键源码：

  • 受理与 ID：source/core/networkrequestmanager.cpp:496-512,952-973。
  • 调度与优先级：source/core/networkrequestmanager.cpp:592-630。
  • 工作执行：source/core/networkrequestrunnable.cpp:35-137。
  • CAS 终态：source/core/networkrequestrunnable.cpp:62-120。
  • 结果转发：source/core/networkrequestmanager.cpp:1130-1189。

Runnable 的 loop.exec() 是 Qt 事件循环，不是忙等。response 信号会退出该局部循环；因此结果发出后才进行 Runnable 清理和 finished(requestId)。

5. 同步入口 sendRequest

sendRequest 在调用线程嵌套事件循环，等待 Manager 结果并执行 callback。它把异步管线包装成“调用线程可等待”的形式，但底层网络仍在工作线程。

边界：

  • bool 返回值表示请求是否被受理，不是 ResponseResult::isSuccess()。
  • blockUserInteraction=true 是默认值，用于避免 UI 在 callback 所需对象被销毁后继续投递。
  • blockUserInteraction=false 不改变工作线程模型，只改变调用方等待方式；callback 生命周期由调用方负责。
  • 同步入口不应与可能重入 Manager 停止/销毁的 callback 混用。

6. 排队、优先级与线程池

  • setMaxThreadCount(int) 控制全局工作线程上限，默认与 CPU 核数相关，合法范围在实现中限制为 1—100。
  • 队列按 behavior.priority 排序；同级保持入队顺序。
  • 队列等待不计入 totalTimeoutMs；总超时从 Runnable 真正开始执行时计时。
  • 下载配置的 threadCount 不增加全局工作线程；MT 下载的多个 Range 请求在同一工作线程/NAM 上异步运行。
  • 线程池满时请求可能长时间排队，因此 UI 应显示“排队/运行”区别，避免将受理当作开始传输。

7. 批次语义

postBatchRequest：

  1. 生成统一 batchId。
  2. 为每个子请求建立 task、session 和结果关联。
  3. 所有子请求共用一个对外 NetworkReply。
  4. 每个子请求完成时发出 requestFinished。
  5. 批次计数归零后由 Manager 发出 batchRequestFinished。

重要限制：batchRequestFinished(batchId, allSuccess) 的 allSuccess 当前取自最后一个结果，不是所有子结果的逻辑与。调用方若要判断整批成功，必须自行累计每个 requestFinished 的错误状态。

8. 进度事件链

  • 进度由 worker 投递事件到 Manager，再由 Manager 发信号，不应由 worker 直接调用 UI。
  • 通用请求不一定发送进度；下载/上传类按 showProgress 与各自实现连接。
  • ProgressThrottle 降低事件频率，但自身没有同步；不要假设它可被多个工作线程无锁共享。
  • MT 下载的进度是通道估算，当前缺少严格分片长度校验，不能作为完整性证明。

9. 取消与停止矩阵

API 当前主要行为 是否保证 Cancelled 终态 适用场景
stopRequest(id) 找到 Runnable 后 quit/abort，移除相关映射并发送失败/取消结果 是，当前实现主动生成 取消一个已受理任务
stopBatchRequests(batchId) 遍历批次内请求，逐项停止并发送结果 是 取消一批任务
stopSessionRequest(sessionId) 找到会话内请求后停止 Runnable，静默移除 Reply 否 调用方不需要完成回调的会话清理
stopAllRequest() 设置停止标志、停止 Runnable、重置映射 否 全局紧急停止/退出清理
工作请求 abort() 中止底层 Reply，经请求完成路径生成错误 通常经 Result 路径，但可能在全局停止时被丢弃 请求内部/定向取消

“已调用停止”不等于“文件已回滚”或“UI 已收到终态”。单线程下载、MT 临时文件、上传源文件在不同停止路径下的状态见第 06 篇。

10. 超时与一次性终态

Runnable 使用 CAS 保证总超时与请求正常结果只有一个被采纳：

  • 总超时先胜出：发送 ErrorCategory::Timeout / TimeoutTotal，退出事件循环。
  • 请求先完成：后续总超时被忽略。
  • abort 后若结果尚未归类为取消或超时，Runnable 将其改为 Cancelled / OperationCancelled。
  • 异常或没有响应的防御路径发送 Unknown / TerminatedWithoutResponse。

总超时、传输超时、idle 超时是不同层次；Qt 5.6 的兼容路径存在默认 idle 关闭时 transfer fallback 不启动的差异，详见第 05 篇。

11. 所有权与销毁

  • m_context 由 Builder/Manager 以 unique_ptr 移交给 Registry 和请求对象。
  • 具体 NetworkRequest 在 Runnable 工作线程创建与销毁。
  • NAM 由池管理，调用方不得删除。
  • 对外 NetworkReply 是 shared_ptr；Manager 移除映射后，外部引用仍可延长其生命周期。
  • Runnable 只有在 run() 完全返回后才通过排队 finished 在主线程销毁，取消运行中请求时尤其依赖这一顺序。
  • unInitialize() 会清理映射，但外部持有 Reply 的调用方仍需自行管理引用和信号连接。

12. 线程安全结论

操作/对象 当前证据 使用建议
结果、进度从 worker 到 Manager 排队信号/事件 可跨线程，接收端应在 Manager 线程处理
全局 SSL 配置 静态 mutex，getter 按值返回 可并发读写，但应在初始化阶段集中配置
全局 proxy、Cookie 路径/Jar 未见与 SSL 同等的全局锁 避免运行中并发修改
Manager 映射、计数、停止 主要在主线程操作，部分 mutex/atomic 保护 停止操作也应在 Manager 所在线程调用
具体 Request、Reply、NAＭ 工作线程亲和 不跨线程直接调用/析构
Registry 自注册启动路径，无运行时并发锁 不要在请求运行中动态注册/修改
ProgressThrottle 无同步 每个请求独占使用，不跨线程共享

13. 注意事项

  1. 主线程必须有可运行的事件循环，否则排队结果、回调和 UI 信号无法及时处理。
  2. 不要在 worker 中直接操作 QWidget 或跨线程删除 NAM/Reply。
  3. 不要把 postRequest 返回非空解释为请求成功，也不要把 sendRequest 返回 true 解释为 HTTP 2xx。
  4. 批次成功不能只依赖 batchRequestFinished 的 allSuccess。
  5. 退出前先停止、等待、断开连接，再反初始化；不要依赖固定等待覆盖所有长请求。
  6. 对 stopSession/stopAll 设计 UI 时，应允许“没有终态回调”的状态存在。
