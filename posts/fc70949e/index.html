简介

本指南聚焦于 OAuth2 认证服务的数据库性能优化，覆盖索引策略、连接池调优、查询性能分析方法、缓存策略、分库分表与读写分离建议、监控指标与基准测试，以及生产环境调优与排障实践。内容基于仓库中的迁移脚本、配置、存储实现与可观测性文档进行系统化梳理，并提供可操作的优化路径。

项目结构

  • 数据库层：PostgreSQL 通过 Drogon ORM 访问；Redis 用于高性能缓存与令牌生命周期管理。
  • 存储抽象：PostgresRepositoryBase 提供主从客户端初始化能力；RedisRepositoryBase 提供 Redis 客户端获取与超时设置。
  • 配置：开发/生产环境分别提供 db_clients 与 redis_clients 的连接池参数。
  • 可观测性：PromExporter 原生导出实际发射的 counter/gauge；histogram 仅日志，当前没有原生延迟直方图。

详细组件分析

索引策略与查询优化（OAuth2 核心表）

  • 表结构与主键
    • oauth2_access_tokens(token PK)、oauth2_refresh_tokens(token PK)、oauth2_codes(code PK)、oauth2_clients(client_id PK)。
  • 索引设计
    • access_tokens: token、client_id、expires_at、(revoked, expires_at) 复合索引。
    • refresh_tokens: token、(revoked, expires_at) 复合索引。
  • 典型查询场景与索引匹配
    • 按 token 精确查找：使用 token 索引。
    • 清理过期/已撤销令牌：使用 (revoked, expires_at) 复合索引加速范围扫描。
    • 按 client_id 统计/过滤：使用 client_id 索引。
  • 建议
    • 避免对大文本字段（scope、redirect_uris）做前缀索引；如需按 scope 过滤，考虑生成列+表达式索引或规范化拆分。
    • 定期 ANALYZE 更新统计信息，确保优化器选择正确计划。
    • 对高频 UPDATE（如 revoked 标记）关注锁竞争与 WAL 压力。

连接池配置与资源管理

  • PostgreSQL 连接池
    • number_of_connections：控制每个 DbClient 的并发连接数。生产环境默认较小，可根据 CPU 核数与负载调整。
    • timeout：连接/语句级超时，防止长事务拖垮池。
    • auto_batch：开启批量提交减少往返。
    • connect_options.statement_timeout：限制单条语句执行时间，避免慢查询占用连接。
  • Redis 连接池
    • number_of_connections：控制 Redis 客户端连接数。
    • timeout：网络/命令超时，避免阻塞线程。
  • 最佳实践
    • 根据 QPS 与平均延迟估算所需连接数：连接数 ≈ QPS × 平均 RTT / 1000。
    • 为不同用途创建多个 DbClient（写/读分离），降低锁竞争。
    • 结合 Hodor 限流保护后端，避免突发流量打满连接池。

查询性能分析方法

  • 慢查询日志
    • 启用 PostgreSQL 慢查询日志（log_min_duration_statement），采集执行时间超过阈值的 SQL。
    • 结合 statement_timeout 快速定位异常长语句。
  • 执行计划分析
    • 使用 EXPLAIN/EXPLAIN ANALYZE 检查索引使用情况、扫描方式与成本。
    • 关注 Seq Scan 出现在大表上的情况，必要时补充索引或改写查询。
  • 瓶颈识别
    • 应用侧没有 PromExporter 延迟直方图；使用 PG 慢查询、Redis 命中率、DB 连接池使用率与外部代理/APM 定位热点。
    • 登录失败、Introspection 错误 Counter 仅在经 IMetrics 实际发射时有数据。

缓存策略建议（Redis 集成与内存优化）

  • Key 设计与 TTL
    • 缓存装饰器使用 fulla:cache: 前缀；独立 Redis 权威/协议仓储仍使用 oauth2:client:、oauth2:code:、oauth2:token: 等键，不能把两层键空间混为一谈。
    • 合理设置 TTL：授权码短 TTL，访问令牌中等 TTL，刷新令牌较长 TTL。
  • 缓存模式
    • 读多写少：先查缓存，未命中再查 DB 并回填；Token 正缓存 TTL 不晚于令牌剩余寿命，单次查询 5 秒 deadline，无 stale positive fallback。
    • 单令牌撤销在 DB 写成功后设置 negative marker，再删除正缓存；family 撤销不清全部正缓存，由 TTL 收敛。
  • 内存优化
    • 监控 Redis 内存与 fulla_cache_total{repo,outcome}，必要时调整 key 空间；引入本地小缓存前须先明确一致性边界。
  • 性能目标参考
    • 缓存命中下的亚毫秒与 P95 数字属于设计目标，不是当前工作区实测。

分库分表策略与读写分离配置

  • 读写分离
    • 通过 PostgresRepositoryBase 的主/读客户端分离，将只读查询路由到副本，减轻主库压力。
    • 注意复制延迟对强一致读的影响，必要时降级到主库。
  • 分库分表
    • 按租户/组织维度水平分片（如按 client_id 哈希），提升横向扩展能力。
    • 令牌表按时间或哈希分片，降低单表体积与锁竞争。
    • 跨分片查询需在上层聚合，避免分布式事务。
  • 迁移与治理
    • 使用迁移脚本逐步切流，灰度验证后再全量切换。
    • 配合监控与告警，观察分片后的均匀性与热点。

性能监控指标与基准测试结果

  • 监控指标
    • 原生 counter/gauge 需实际发射并注册；请求 Counter 按状态码增量，登录失败与 Introspection/Revocation 错误仅在发射时有数据。
    • 应用侧没有原生延迟直方图；P95/P99 使用外部代理/APM 或压测驱动。oauth2_active_tokens 是签发活动标记。
  • 基准目标（参考设计文档，不是当前实测）
    • 令牌操作：授权码生成 < 10ms，令牌交换 < 50ms，Introspection 缓存命中 < 10ms、未命中 < 30ms。
    • 数据库查询：索引命中 < 5ms，撤销更新 < 10ms。
    • 负载：稳定 1000 req/s（P95 < 50ms），峰值 5000 req/s（P95 < 100ms），突发 10000 req/s（P95 < 200ms）。
    • 缓存：正常负载下命中率 ≥ 95%，Redis 操作 < 2ms。
  • 基准测试
    • 项目包含轻量性能基准用例；本页未执行测试。未发布 capacity driver 与共享 runner 只验证工具行为，不形成当前容量 baseline。

v1.6.0 热路径修复与发布基准门禁

v1.6.0 发布前的五场景基准门禁（同机背靠背对上一发布版 + 重复臂 + 同窗对照）抓到
两个”每请求多一次 DB 往返”的回归，均在同一基准战役中发现并修复（各吃掉所在场景
17–18% QPS）；复测后 userinfo / introspect 回到 v1.5.0 的 **97–112%**。

  • 修复一：userinfo / 签发路径的 claim_mappings 查询（v1.6.0）
    • 问题：StorageClaimMappingsProvider 无缓存，userinfo / code / refresh 每次签发
      都查一遍 claim_mappings 表。
    • 修复：CachedClaimMappingsProvider 装饰器——保持 provider 契约不变，把已启用映射
      列表缓存在进程内存：
      • 每个声明映射写路径都调用 invalidate()（与刷新 discovery claims_supported
        的同一批钩子），CRUD 立即可见（PublicationChain e2e 语义保持）；
      • TTL（默认 60s）仅用于约束跨进程漂移（多实例部署下别的进程写入的过期上限，
        best-effort）；本进程写路径不走 TTL；
      • 启动后第一个请求仍可能回源一次（惰性），内存模式部署保持零接线。
  • 修复二：introspection 的 oauth2_client_owners 查询（v1.6.0）
    • 问题：v1.4.0 的 P1-4 组织覆盖逻辑让 introspection 每次调用都读
      oauth2_client_owners。
    • 修复：插件内 3s→60s TTL 缓存（快路径：锁+查表、零分配），从两处 owner 行写
      路径精确失效      （开放平台 suspend/resume；组织软删除级联，提交后失效）。
      OrgLifecycle / ClaimsMapping 语义经 e2e 验证不变（删除→introspection 失效、
      CRUD→即时发布均绿）。
  • 基准门禁本身（benchmarks/）：场景脚本 s1-discovery、s2-client-credentials、
    s3-introspect、s4-auth-code、s5-refresh-token、s6-userinfo；v1.6.0 运行记录在
    results/20261027-3d458c08-*.json（发现 S6 userinfo −18%、S3 introspect −17%；
    修复后 S6 97–112%、S3 同窗 103%）。方法论要点：只与同日同机臂对比——跨日基线
    存在 ±9% 主机漂移，不可作为回归依据。
  • 相关schema侧变化（v1.6.0）：users.custom_attributes 带 GIN 索引（V044）；
    audit_logs 月度分区的保留 DROP 与分区创建同锁定周期执行（P1-6）。

性能考量

  • 索引与查询
    • 优先利用现有复合索引；对复杂过滤条件评估表达式索引或物化视图。
    • 避免 SELECT *，仅拉取必要字段以减少 IO 与序列化开销。
  • 连接池与超时
    • 根据负载曲线动态调整 number_of_connections；设置合理的 timeout 与 statement_timeout。
    • 使用 auto_batch 合并写操作，降低网络往返。
  • 缓存与一致性
    • 按当前撤销顺序：DB 写成功后设 negative marker，再失效正缓存；不要概括为“先删缓存再更新 DB”。
    • 正缓存 TTL 不超过令牌剩余寿命；family 撤销的残留正缓存由 TTL 收敛。
  • 监控与告警
    • QPS 与 P99 使用外部指标；原生 Counter 告警仅用于实际发射的登录失败、Introspection/Revocation 错误等，不把请求 Counter 的 rate 当 QPS。
    • 结合慢查询日志与执行计划持续优化。

故障排查指南

  • 连接池耗尽
    • 现象：出现连接耗尽错误、数据库连接数飙升。
    • 排查：检查 number_of_connections、timeout、statement_timeout；确认是否存在长事务或未释放连接。
    • 验证：通过连接池行为测试用例观察复用情况。
  • 慢查询与锁竞争
    • 现象：P99 延迟升高、CPU/IO 打满。
    • 排查：启用慢查询日志，分析 EXPLAIN 计划；检查索引缺失或失效；评估锁等待。
  • 缓存穿透/雪崩
    • 现象：大量请求直达 DB，Redis 命中率骤降。
    • 排查：增加空值缓存、随机 TTL、热点 Key 预热；限制并发穿透。
  • 指标异常
    • 现象：实际发射的 Counter/Gauge 或外部 QPS/P99 指标异常。
    • 排查：结合日志与指标定位热点端点；检查下游依赖（DB/Redis）健康状态；不要查询不存在的应用侧 histogram bucket。

  • tests/security/injection/DbLeakVerificationTest.cc:79-143
  • docs/operate/observability.md:1-22

结论

索引、连接池与缓存策略需结合慢查询、执行计划和受控基准验证。应用请求 Counter、活跃令牌 Gauge 与日志 histogram 都不能直接替代 QPS、活跃 Token 数或 P99；v1.6.0 历史门禁也不是当前容量证明。
