构建体系：CMake、QMake 与平台差异

发表于2026-11-25|更新于2026-11-25|开发工具构建系统
|浏览量:
项目/qt-network-request/构建与环境
qt-network-request实践指南进阶

1. 定位与结论

本篇回答“使用什么工具链、如何选择 Qt、不同构建入口是否等价、哪些平台兼容来自代码而非猜测”。核心结论：

  • 主构建入口是 CMake 3.15+，固定 C++14；库目标是共享库 QNetworkRequest。
  • Qt 6 必须显式设置 USE_QT6=ON。根配置注释虽写“先尝试 Qt6 再回退 Qt5”，实际分支没有自动探测或回退。
  • 即使关闭示例与测试，CMake 仍 REQUIRED 查找 Qt Widgets、Xml、Test；纯库消费者也会配置完整 GUI/测试模块。
  • CMake 与 QMake 都保留，但产物布局、静态库能力、OpenSSL 处理和安装导出并不等价。
  • Qt 5.6.3 + MSVC 2015 是近期提交明确的兼容目标；CI 只验证 Qt 5.15.2 + VS 2022/Ubuntu/macOS，不能把最低兼容目标当作已验证矩阵。
  • Conan/vcpkg 仍是未闭环集成：Conan 的 shared=False 未映射到 CMake，vcpkg 的源地址、校验和与 Qt6 feature 传递存在占位/断点。
  • 手工 gzip 解压依赖 zlib；Qt 自身自动解压不应与手动解压重复执行，详见第 05 篇。

2. 工具链与依赖基线

项目 已确认要求/选择 证据与边界
CMake ≥ 3.15 CMakeLists.txt:4-5；不代表脚本所用全部语法已在最低版本逐一验证
C++ C++14，必需 CMakeLists.txt:7-11；目的是兼容 Qt 5.6 配套工具链
Qt5 find_package(Qt5 5.6 COMPONENTS Core Widgets Network Xml Test REQUIRED) CMakeLists.txt:35-38；库自身仅链接 Core/Network
Qt6 显式 USE_QT6=ON，同样查找五组件 CMakeLists.txt:30-34；CI 未覆盖
OpenSSL Linux 必须找到；macOS 缺失仅警告；Windows 复制随仓库 DLL cmake/openssl.cmake:4-41、cmake/utilities.cmake:23-43
zlib 手工响应解压路径需要 以实际源码 #include <zlib.h> 与链接配置为准；不要因 Qt Network 能自动解压而删除该依赖
MSVC CRT 强制动态 CRT：Debug /MDd，其余配置 /MD cmake/compiler-flags.cmake:4-28；与静态 CRT 包管理器 triplet 不匹配

Windows OpenSSL 选择只看 Qt5 小版本：Qt5 < 5.12 使用 ThirdParty/openssl/1.0.2/bin，其他情况使用 1.1.1/bin（source/CMakeLists.txt:98-107）。这是仓库约定，不检测系统已安装版本，也不校验 DLL 哈希；Qt6 新版本若改变运行时需求，不能沿用该假设直接发布。

3. CMake：目标、产物与安装

3.1 目标关系

source/CMakeLists.txt:5-64 显式枚举实现、私有头与 16 个公共头。source/CMakeLists.txt:89-110 说明库的 Qt/OpenSSL 依赖。

所有目标通过 set_output_directories() 输出到 QTNETWORK_OUTPUT_ROOT/<Config>；默认根为 CMake 二进制目录（cmake/utilities.cmake:8-18）。因此库、示例和九组测试 exe 通常都在 build/Release/ 或 build/Debug/；build/test/ 是测试子目录和 CTest 注册上下文，不是测试 exe 的输出目录。Windows 后构建将主库 DLL 与 OpenSSL DLL 复制到依赖目标旁边。

安装规则导出 QtNetworkRequest::QNetworkRequest 与版本文件（source/CMakeLists.txt:112-154）。但：

  • cmake/QtNetworkRequestConfig.cmake.in:1-8 不调用 find_dependency(Qt5/Qt6)；
  • 公共头直接依赖 Qt 类型，消费者必须自行 find_package 并链接 Qt Core/Network；
  • Qt 依赖在库目标中是 PRIVATE；共享库安装不能自动把 Qt 头文件/依赖目标带进消费者工程；
  • 同主版本兼容，无 SOVERSION；不能据此承诺跨主版本二进制兼容；
  • 当前没有 BUILD_SHARED_LIBS 或静态库选项，CMake 明确 add_library(... SHARED)。

4. QMake：保留的第二入口

根 QtNetworkRequest.pro:2-8 组织 qnetworkrequest/samples/tests 子项目。source/QNetworkRequest.pro：

  • QT += network、移除 gui，启用 qt/thread；
  • 按 Qt 版本补 C++14 标志；
  • Debug 目标名追加 d，即 QNetworkRequestd；
  • 输出 Debug/Release 到仓库 build/ 下；
  • staticlib 配置可添加 QT_MTNETWORK_STATIC，与 CMake 固定共享库不同；
  • 未复制 Windows OpenSSL DLL，也未导出 CMake 安装包；
  • Qt6/QRecursiveMutex 由 qmake 的版本条件定义。

因此“CMake 构建成功”不能直接证明 QMake 构建成功，反之亦然。调试 DLL 名称、运行目录、宏定义与安装产物必须按实际入口记录。测试范围也不同：CMake 注册九组测试，而 QMake 的 test/test.pro:1-27 只构建核心 UnitTests（main.cpp、test_networkrequest.cpp、httptestserver.cpp）。CMake 未设置 DEBUG_POSTFIX，Debug 库仍叫 QNetworkRequest；QNetworkRequestd 只是 QMake 规则。

5. 平台构建脚本

入口 行为 注意事项
scripts/build_win.bat 检查 QT_DIR/QTDIR，检测 VS 2017/2019/2022，清理仓库 build/install，CMake x64 Release :111-126 会删除旧 build/install；仅识别 Professional/Community；不自动设置 CMake prefix，依赖环境缓存
scripts/test.bat 从当前目录向上找仓库根，检测 Qt/VS，支持 /clean /nobuild /debug :39-58 特意不用不可靠的 %~dp0；/clean 删除 build；/nobuild 仍要求已有正确 CMake 缓存
scripts/build_linux.sh 必须从 scripts/ 运行；可 Debug/Release、指定 Qt 路径、prefix、tests :106-114 工作目录有约束；:228-241 测试失败只警告，最终仍打印完成，不能以退出码单独判断测试通过
scripts/build_macos.sh 同样从 scripts/ 运行；尝试 Homebrew OpenSSL 1.1/3；支持 --arch :125-140 未把检测到的 Qt 主版本映射为 USE_QT6；Qt6 环境可能仍配置 Qt5
scripts/build_and_pack.bat 串联 build_win 与 pack 会先清理构建，再清理 install/installer；属于破坏性本地发布流程，执行前需备份
scripts/pack.bat 收集 Release 产物、windeployqt、WiX 构建 MSI WXS 文件名与当前 exe 不一致，当前链路不能视为可发布，详见第 14 篇

Linux/macOS 脚本的 Qt 自动探测只设置 Qt5_DIR/Qt6_DIR 提示，并不等价于根 CMake 的 USE_QT6 选择。使用 --qt-version 6 前必须核对最终 configure 参数与 CMakeCache。

6. QtCompat：集中兼容策略

source/core/qtcompat.h 是 Qt 版本差异的集中适配层，覆盖传输超时、错误信号、HTTP/2、TLS 1.3、递归互斥、字符串拆分等。维护规则：

  1. 新代码通过适配函数使用 Qt API，不再散落 #if QT_VERSION。
  2. 最低版本 Qt 5.6.3 的“无实现”分支必须配业务层兜底，不能只做到可编译。
  3. Qt5.15 与 Qt6 的运行时行为仍需测试；宏能编译不代表 TLS、HTTP/2、事件时序一致。
  4. 更新 Qt 基线时同时检查 OpenSSL、部署运行时、CMake、QMake、Conan 和 CI。

已确认的重要限制：Qt <5.15 的 setTransferTimeout() 是空实现（source/core/qtcompat.h）。transferTimeout 并非所有支持 Qt 上都生效， heartbeat 又仅在 idleTimeoutMs > 0 时启动，详见第 05 篇。

7. Conan 与 vcpkg 现状

Conan

conanfile.py：

  • 版本 2.2.1，默认 Qt5、shared、fPIC；C++14。
  • 依赖 Qt 5.15.8 或 Qt 6.5.3、OpenSSL 1.1.1w。
  • 声明最低 MSVC 190/GCC 5/Clang 3.5/Apple Clang 7，但版本比较与真实工具链兼容仍需实测。
  • package_id() 通过 Qt 完整版本区分 ABI，删除 qt 选项本身。
  • package_info() 补充 Qt Core/Network 消费依赖；Qt6 还列 OpenSSL。
  • 关键断点：shared=False 未转为 CMake 配置，库仍固定 SHARED；Windows 动态 CRT 与 CMake 强制 /MD 相符，但不能据此宣称支持静态包。
  • author、仓库 URL 仍为占位值。

vcpkg

ports/qtnetworkrequest/vcpkg.json 与 portfile.cmake：

  • manifest 版本 2.1.6，与根 CMake 2.2.1/Changelog 2.3.0 不一致。
  • REPO your-org/... 和全零 SHA512 是占位值，正式拉取不可能按当前配置验证。
  • vcpkg_check_features() 生成 FEATURE_OPTIONS，但未并入 CONFIGURE_OPTIONS；USE_QT6 实际不会由该列表传入。
  • vcpkg_check_linkage(ONLY_DYNAMIC_CRT) 与 CMake 动态 CRT 一致。
  • usage 写“9 public headers”，当前安装规则实际覆盖 16 个。
  • Qt6 feature 的 CMAKE_DISABLE_FIND_PACKAGE_Qt5 只有变量被设置，Qt6 选择仍依赖未传通的 USE_QT6。
  • 两个 feature 只声明 Qt Core/Network，而根 CMake 即使关闭示例/测试仍 REQUIRED Widgets/Xml/Test；修复占位源后，隔离的 vcpkg 环境仍可能缺组件。
