认证、代理、TLS 与 Cookie 配置

AR##-进阶
发表于2026-11-25|更新于2026-11-25|框架库Qt框架
|浏览量:
项目/qt-network-request/设计与架构
qt-network-request架构设计进阶

证据基线：master @ 6c25067；静态代码核查，未执行真实认证、TLS 或代理服务器测试。

1. 背景

网络安全配置分散在公共配置结构、请求基类、线程亲和 QNetworkAccessManager、OAuth2 Token 请求和 GUI 示例中。仅查看 AuthConfig 或 README 会高估实际覆盖：请求类型不同，认证注入路径并不完全一致；GUI 也不暴露全部库级安全选项。

2. 核心结论

  1. 库支持 None、Basic、Bearer、API Key、OAuth2；未实现 Digest。OAuth2 grant 支持 client credentials、password、refresh token，Authorization Code + PKCE 明确不在当前范围。
  2. 普通请求由 NetworkRequest::prepareRequest() 统一构造 URL、Header、认证和 SSL；上传与多线程下载自行构造请求，不能假定拥有完全相同的认证行为。
  3. Basic/Bearer/OAuth2 使用 Authorization Header；API Key 可放 Header 或 Query。用户自定义 Header 优先，认证配置不会覆盖同名 Header。
  4. OAuth2 Token 预取目前只在 NetworkCommonRequest 中实现；上传与下载没有相同的 Token 预取路径。
  5. OAuth2 Token 缓存是进程级内存缓存，有互斥保护，但缓存键和刷新语义存在明确边界，不能视为完整 OAuth2 客户端。
  6. SSL 安全默认值为 VerifyPeer + TLS 1.2 + Never Ignore + System CA；全局配置会把 Inherit 规范化为安全默认值。
  7. 代理按“NAM 获取时应用全局/默认 → 请求准备时应用逐请求覆盖”的顺序工作；Cookie 则由全局 jar 和线程本地 wrapper 共享。

3. 认证配置与注入规则

认证类型 配置要点 实际注入 限制
None 默认类型 不注入认证 无
Basic username/password Basic base64(username:password) 用户名空时 isValid() 为 false
Bearer 原始 token 自动添加 Bearer 前缀 不要再重复填写前缀
API Key apiKey/apiValue/placement Header 或 URL Query Query 方式可能进入日志与历史 URL
OAuth2 grant、Token URL、client、scope、凭据 普通请求异步取 Token 后写 Bearer 不是所有 RequestType 都接线

3.1 Header 优先级

prepareRequest() 先写入 RequestContext::headers，随后调用 applyAuthConfig()：

  • Authorization 检查大小写两种常见写法，用户已设置时不覆盖。
  • API Key Header 使用请求对象自身的 hasRawHeader() 判断。
  • Body 类型推导的 Content-Type 也遵循“用户已设置则不覆盖”的原则。

依据：source/requests/networkrequest.cpp:411-422、source/requests/networkrequest.cpp:525-558。

3.2 API Key Query

Query 形态 API Key 在构造最终 QUrl 时通过 QUrlQuery::addQueryItem() 追加，和显式 queryParams 一起进入 URL。它不会走认证 Header 覆盖规则。调用者应意识到完整 URL 可能被记录、收藏或展示。

依据：source/requests/networkrequest.cpp:387-406。

4. OAuth2 生命周期与实际边界

4.1 普通请求路径

  1. NetworkCommonRequest 根据 Token URL、client ID、grant 和 scopes 生成缓存键。
  2. 命中且未过期的缓存时直接使用 access token。
  3. 未命中时向 Token URL 发送 application/x-www-form-urlencoded POST。
  4. 解析 JSON 的 access_token、可选 refresh_token 和 expires_in，写入内存缓存。
  5. 将 access token 写入当前请求的 AuthConfig::token，继续原请求。

依据：source/requests/networkcommonrequest.cpp:249-345。

4.2 缓存边界

  • 缓存键为 tokenUrl | clientId | grant | scopes。
  • 键中不包含 username、password、client secret 或 refresh token。
  • find/store/clear 有 QMutex 保护，但“检查缓存→发起 Token 请求→写回”没有并发合并机制。
  • 缓存仅存在进程内存，不落盘；expires_in 缺省按 3600 秒处理。

这些是代码事实，不自动等于安全事故；但多账号复用同一 client/grant/scope 时，必须由调用者确认缓存隔离是否足够。

依据：source/features/oauth2tokencache.cpp:33-67、source/requests/networkcommonrequest.cpp:253-265、source/requests/networkcommonrequest.cpp:321-339。

4.3 401 自动刷新不是通用能力

只有同时满足以下条件才触发一次刷新：

  • 原请求收到 HTTP 401；
  • 认证类型为 OAuth2；
  • 当前请求尚未刷新过；
  • 配置中已有非空 refresh token。

触发后只把 grant 切为 RefreshToken 并重启当前请求。Token 响应中的新 refresh token 被写入缓存，但没有回填原 AuthConfig。因此：

  • client credentials 和 password grant 默认不能靠 401 自动续期；
  • “任意 OAuth2 请求都会自动刷新”是错误理解；
  • 上传/下载没有普通请求的 Token 预取路径。

依据：source/requests/networkrequest.cpp:461-486、source/requests/networkcommonrequest.cpp:334-342、source/requests/networkuploadrequest.cpp:92-118、source/requests/networkmtdownloadrequest.cpp:364-380。

5. 代理配置

ProxyConfig 默认禁用，默认类型为 HTTP Proxy，默认端口 1080；有用户名密码时一并构造 QNetworkProxy。

有效顺序：

  1. 获取线程 NAM 时，全局代理启用则设置全局代理，否则恢复 QNetworkProxy::DefaultProxy。
  2. 请求准备阶段，逐请求代理启用则覆盖 NAM 代理；否则使用全局代理；两者都禁用时不额外修改。
  3. 下一次从池中获取该线程 NAM 时，会再次按全局/默认值重置，再进入逐请求覆盖。

依据：include/proxyconfig.h:35-50、source/core/networkaccessmanagerpool.cpp:25-36、source/core/networkaccessmanagerpool.cpp:81-88、source/requests/networkrequest.cpp:160-172、source/requests/networkrequest.cpp:375-376。

注意：代理认证密码是配置值；GUI 保存请求时可能把它写入 JSON，详见第 7 节。

6. TLS/SSL 配置

6.1 默认与继承

字段 安全默认 继承规则
peerVerifyMode VerifyPeer 逐请求 Inherit 使用全局值
minProtocol TlsV1_2 Qt < 5.12 的 TLS 1.3 设置会降级
ignoreSslErrorsPolicy Never 可配置为忽略全部或指定错误
caPolicy SystemDefault Custom 使用请求提供的 CA 列表

全局配置中的 Inherit 不是“无限继承”，而是由 setGlobalSslConfig() 替换为安全默认值。读取全局配置返回副本，避免工作线程引用并发修改的全局对象。

依据：include/sslconfig.h:42-93、source/core/networkrequestmanager.cpp:879-903、source/core/qtcompat.h:92-96。

6.2 应用范围

  • 普通请求：prepareRequest() 调用 applySslConfig()。
  • 上传：HTTP/HTTPS 分支应用 SSL；FTP 代理分支不进入同一路径。
  • 多线程下载：探测和分片路径分别应用 SSL，分片还有错误处理。
  • QtRequester：没有独立 SSL 配置界面，主要使用库默认值；代理配置可在 GUI 中设置。

安全边界：IgnorePolicy::Always 和 VerifyNone 是显式不安全选项，不能把“可配置”理解为推荐生产配置。

7. Cookie 模型与敏感数据

7.1 持久化 Cookie

PersistentCookieJar 使用 JSON 数组保存 name、value、domain、path、secure、httponly 和 expiration：

  • 构造时若路径非空则加载；
  • 收到响应 Cookie 且集合发生变化时保存；
  • 析构时再次保存；
  • 手动 insertCookie() 不会触发同样的即时保存逻辑。

依据：source/infra/networkcookiejar.cpp:13-24、source/infra/networkcookiejar.cpp:38-90、source/infra/networkcookiejar.cpp:98-139。

7.2 共享边界

Manager 持有全局 jar。每个线程的 NAM 通过非拥有 SharedCookieJar wrapper 委托到同一 jar；没有配置存储路径时，池会将 NAM 的 CookieJar 设为 null。QtRequester 未配置持久化路径时只展示响应 Cookie，不等于启用跨请求 Cookie 存储。

依据：source/core/networkrequestmanager.cpp:907-921、source/core/networkaccessmanagerpool.cpp:38-53、source/infra/sharedcookiejar.h:25-48。

7.3 凭据与日志

当前环境、集合、单请求 JSON 和 Cookie 文件都是明文结构；库日志可能输出完整 URL，认证挑战处理还会输出响应体。API Key Query、Bearer Token、client secret、代理密码和 Cookie value 都可能进入这些位置。

调用者应：

  • 不把含真实凭据的配置提交到版本库；
  • 在分享集合或日志前脱敏；
  • 避免把 Query API Key 放入可审计 URL；
  • 对本地配置文件设置适当的文件权限和备份策略。
